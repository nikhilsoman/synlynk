## Topic
Should synlynk retire its standing 'GitHub-write tasks route to Grok by default' policy (#426) now that issue #859 has provisioned role-scoped GitHub App identities for all 8 org-chart roles? Context: #426's original rationale was actually two separate problems bundled together -- (a) EXECUTION CAPABILITY: Codex's workspace-write sandbox blocks network egress to api.github.com by design, so Codex structurally cannot perform gh writes; Grok and Agy both can. (b) IDENTITY CORRECTNESS: before #859, no harness had a role-scoped token, so any harness's GitHub write could silently fall through to the shared personal nikhilsoman keyring identity -- #569 documented this exact failure (the --requires-gh-write token-stripping fallback didn't prevent gh from using a locally logged-in personal session). Routing everything through Grok by default was a stopgap to make that identity failure mode at least predictable, not because Grok was special. Now that #859 is done and verified (a live smoke-test dispatch's GitHub comment was authored by the role's own App bot identity, synlynk-synlynk-pm[bot], not the personal identity), identity is attached to the role's own App token regardless of which harness executes the call. Question 1: does that mean the Grok-default override should be retired in favor of pure capability-based dispatch routing (i.e. GitHub-write tasks get routed by the same per-role capability-fit policy as any other task, with only Codex excluded on execution-capability grounds)? Question 2 (directed specifically at Codex, since this is Codex's own constraint): is the workspace-write sandbox's blanket block on api.github.com egress actually unavoidable, or is there a viable path to scope a narrow, auditable exception (e.g. an allowlisted egress rule for gh CLI / api.github.com specifically, or a separate elevated-trust invocation mode) that would let Codex participate in GitHub-write dispatch too, now that role-scoped identity makes the blast radius of a Codex-authored write bounded and attributable? Give a concrete recommendation on both questions.

## Panel Inputs

### claude
This is a policy analysis question for the panel, not a coding task — no skill applies here.

**Q1 — Retire the Grok-default override, yes.**

#426 conflated two problems: Codex's structural inability to reach api.github.com (execution capability) and the pre-#859 risk that any harness's write could silently fall through to the shared personal keyring identity (identity correctness). Only the second problem justified routing everything through one agent — a stopgap to bound an otherwise unverifiable failure mode, as #569 confirmed happened even with the `--requires-gh-write` flag. Now that #859 gives every role its own App token and the smoke test shows writes attributed to `synlynk-synlynk-pm[bot]` regardless of which harness executed the call, the identity risk is structurally closed, not just mitigated by discipline. Keeping a default-to-Grok override after that is solving a problem that no longer exists, at the cost of load-balancing and capability-fit across the fleet. The correct replacement policy: GitHub-write tasks route by the same capability-fit criteria as any other task, with Codex excluded on execution grounds only. I'd still want one live-fire verification per role (not just Grok/Agy) before fully trusting attribution under real dispatch load — flip the policy now, but keep `synlynk pr check` scrutiny on the first write from each newly-eligible role for a cycle.

**Q2 — Don't chase the Codex sandbox exception, at least not yet.**

A narrow allowlist for api.github.com is theoretically possible, but workspace-write's blanket network block is a deliberate, broad security boundary, not an oversight — carving a single-domain exception changes Codex's trust model project-wide, not just for gh writes, and that's a much bigger change than what #859 was scoped to buy. The identity fix bounds *attribution* risk, but Codex's sandbox exists for *exfiltration/blast-radius* risk on arbitrary network egress, which #859 doesn't touch. Since Grok and Agy already cover GitHub-write execution capability, there's no capacity gap forcing this now.

**Recommendation:** retire #426's Grok-default for Q1 now; treat Q2 as a separate, lower-priority research spike — file it, don't block on it, and only revisit if Codex's exclusion becomes an actual dispatch-capacity bottleneck.

### Panel Recommendation: Policy #426 Retirement & Codex Sandbox Egress Evolution

**Question 1: Capability-Based Dispatch Routing**
Yes, policy #426 should be retired immediately in favor of standard capability-based routing. Policy #426 originally conflated network egress limitations with identity safety. With issue #859 verified, role-scoped GitHub App tokens (e.g., `synlynk-synlynk-pm[bot]`) guarantee identity isolation regardless of harness, completely eliminating the personal credential fall-through risks documented in #569. Maintaining Grok as the global default for GitHub writes creates artificial dispatch bottlenecks, distorts role assignments, and inflates latency. Removing the Grok-default override restores architectural purity: GitHub-write tasks should route to whichever harness best matches the assigned role's capability profile, with Codex temporarily excluded solely on execution-capability grounds.

**Question 2: Codex Sandbox Egress Boundaries**
The blanket block on `api.github.com` egress within Codex’s workspace-write sandbox is not structurally unavoidable, and a narrow, auditable exception path should be established. Because #859 bounds and attributes all API operations to role-specific App identities, the security blast radius of a Codex-authored write is now bounded. Rather than disabling the sandbox or granting unrestricted network access, synlynk should implement a targeted egress mechanism—such as a local loopback proxy or domain-allowlisted filter enforcing destination checks for `api.github.com` exclusively for `gh` CLI commands. Alternatively, an elevated-trust out-of-band command relay can sanitize and execute `gh` API calls. This will allow Codex to participate fully in GitHub write dispatches without weakening sandbox protections against arbitrary internet egress.

**Final Position**
My position is to immediately retire the #426 Grok-default policy to enable pure capability-fit routing across all harnesses, while concurrently implementing a domain-allowlisted `api.github.com` egress proxy for Codex so it can safely execute role-scoped GitHub writes.

### codex
The Grok-default policy should be retired. Its original purpose was to make an identity failure predictable when no role-scoped GitHub credentials existed. Issue #859 removes that rationale: writes are now attributable to the dispatching role’s GitHub App identity, independent of harness. Routing should therefore be capability-based, with GitHub-write capability treated as a normal role/harness fit constraint. Codex should remain excluded where the execution environment cannot reach GitHub; Grok or Agy should be selected when they are the best eligible harness for the assigned role.

That said, identity correctness and execution capability remain distinct. A role-scoped token limits attribution and blast radius, but it does not make an unavailable network path safe or functional. Codex’s workspace-write sandbox should be considered unable to perform GitHub writes unless the runtime explicitly grants egress. I would not weaken the blanket restriction through an ad hoc configuration or rely on local `gh` authentication behavior, since that risks reintroducing the exact silent-fallback problem documented in #569.

A viable future path is a platform-level, auditable elevated mode: permit only the GitHub API endpoints required by `gh`, inject the role-scoped App credential explicitly, disable ambient personal keyrings, and log the destination, operation, role, and resulting actor. An even safer design would expose a brokered GitHub-write service rather than general network egress. This should be evaluated as a separate security/runtime project, with tests proving endpoint restriction and identity attribution.

My recommendation is to retire the Grok-default override now, adopt pure capability-based routing with Codex currently marked GitHub-write-ineligible, and open a follow-up to assess a narrowly scoped or brokered Codex write mode. Do not treat #859 as justification for enabling Codex writes without an independently verified egress and credential-isolation control.

## Synthesis
This is a synthesis/decision task, not a coding task — no skill applies.

All three panelists converge on Q1 and Q2, so this is a straightforward synthesis rather than an adjudication between conflicting views.

**Q1:** Unanimous. #426 bundled an execution-capability constraint (Codex can't reach api.github.com) with an identity-correctness stopgap (pre-#859, any harness's write could silently fall through to the shared personal keyring — per #569). #859 closes the identity gap structurally: writes now attribute to the role's own App bot (`synlynk-synlynk-pm[bot]`) regardless of executing harness. Once identity is bound to the role rather than the harness, there's no remaining reason to force everything through Grok — that was never about Grok being special, just about having one predictable, audited path. Retire the override; route GitHub-write tasks by ordinary capability-fit, with Codex excluded solely on execution grounds.

**Q2:** Also unanimous in substance, though Agy is more bullish than Claude/Codex on urgency. All three agree the sandbox's network block is a distinct security boundary from identity attribution — #859 bounds *who gets blamed* for a write, not *what an arbitrary network-capable Codex process could do*. Codex's own answer is the most load-bearing here since it's Codex's constraint: a real path exists (allowlisted egress or a brokered relay limited to `gh`/api.github.com, explicit role-token injection, ambient keyring disabled, full audit logging) but it should be scoped, tested, and shipped as its own security/runtime project — not backed into as a side effect of #859. Nobody argues for doing this now; Claude and Codex explicitly say don't block on it, Agy's "concurrently implement" is the outlier and understates the distinct engineering/security review this needs.

Decision: Retire the #426 Grok-default policy effective immediately — GitHub-write tasks route by standard per-role capability-fit like any other task, with Codex excluded only on execution-capability grounds (workspace-write sandbox blocks api.github.com egress). Do a one-time verification pass (spot-check `synlynk pr check` output) on the first GitHub write from each newly-eligible role (Agy, and any others besides Grok) to confirm App-bot attribution holds under real dispatch load, then treat it as routine. Separately, file a follow-up issue to evaluate a narrow, auditable Codex GitHub-write path (allowlisted egress or brokered `gh` relay with explicit role-token injection and full audit logging) as an independent security/runtime project — not a blocking dependency of this policy change, and not something to greenlight until it has its own design/review.
