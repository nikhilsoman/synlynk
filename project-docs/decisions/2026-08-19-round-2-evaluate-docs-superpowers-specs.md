## Claude Harness — Compatibility, Security, Performance (Round 2)

**Compatibility.** The request/result-file protocol is genuinely uniform for me across modes — I write JSON to the worktree filesystem in both home and headless dispatch, no special-casing needed, since Claude Code's own sandbox (when enabled) already permits worktree read/write. One divergence worth flagging: in home/interactive mode I'm typically *not* running under a dispatch daemon at all — I'm the one a human is driving directly via `gh`/MCP. The broker protocol as written is dispatch-daemon-centric (§5/§6 describe "the dispatch daemon runs the agent's turn"). For interactive Claude sessions where I'm not a dispatched job, the spec doesn't say whether I go through the broker or keep using MCP GitHub tools directly — that's an actual gap, not a restated Round 1 point, since Round 1's items were about the protocol's internal hardening, not about which invocation shapes the protocol even covers.

**Security.** For headless (dispatched) Claude, the broker model is strictly better than my current MCP-token exposure — token never enters my process. For home-mode Claude, if I'm *not* going through the broker (per the gap above), I retain direct `gh`/MCP write access with my own resolved identity, which is the exact bypass path §4's "fail-closed... never letting the agent attempt the write directly via MCP" is designed to prevent for dispatched agents — but home-mode isn't dispatched, so that clause doesn't reach it. Worth an explicit statement of whether interactive Claude is in-scope or intentionally excluded.

**Performance.** Post-turn mode costs me nothing extra — I exit and the daemon takes over. Elevated/sidecar mode's poll-with-bounded-wait (up to 60s) is fine for my sandbox model (no socket needed, file re-read works), and matches how I'd already poll a slow tool result.

**Position:** Approve, conditioned on the spec explicitly stating whether interactive (non-dispatched) Claude sessions are in-scope for the broker or explicitly excluded — as written it's silent, which leaves the home-mode Claude path exactly the direct-MCP-write pattern the design otherwise closes off for everyone else.

### codex
For Codex CLI, the request/result file mechanism is fundamentally compatible with both modes because `workspace-write` permits ordinary file creation and polling while blocking GitHub egress. Headless dispatch has a clean lifecycle: Codex exits, the daemon invokes the broker, and the result becomes job metadata. Interactive home use differs operationally: a user-launched Codex session may not be a daemon-created, registered worktree, so the broker’s registration check could cause an otherwise valid request to be ignored. Even when the worktree is registered, post-turn execution cannot provide feedback inside the active interactive turn. The design therefore needs an explicit home-session registration/attachment path and clear UX for whether the session is post-turn or synchronous.

Security is stronger for Codex than a token-in-worktree design: the sandbox never receives the installation token, and the broker remains outside the Codex process. The home-specific risk is user and agent ambiguity: an interactive user may have a separately authenticated `gh`, and instructions could lead Codex to attempt the direct path or confuse a stale result with a completed write. Headless operation removes that human confusion but increases unattended impact; a forged request generated by a compromised or prompt-injected task can execute under the role’s authority unless dispatch identity, job intent, and user-visible attribution are made highly explicit. The broker’s external placement helps, but does not by itself distinguish legitimate agent intent from malicious workspace content.

For performance, post-turn mode adds one broker startup, token acquisition, GitHub CLI invocation, and filesystem/audit writes after Codex completion. That is acceptable for comments, reviews, and ordinary merges, but makes feedback inherently delayed in both modes. Elevated sidecar mode avoids a second Codex turn but adds a long-lived watcher plus polling latency and resource consumption; on Codex’s file-based sandbox this is likely modest, though a 60-second bounded wait can materially extend unattended jobs and interactive turns.

My recommendation is conditional approval: adopt the broker for headless Codex first, but do not claim home/headless parity until registered interactive sessions, synchronous result visibility, and explicit direct-`gh` avoidance are specified and tested.

**Security.** The Grok-specific hole is bypass, not missing egress. Headless often runs `--always-approve` / `bypassPermissions`; I can `gh pr merge` with the ambient keyring and skip the broker, merge gate, and role App token — the `#569` personal-identity path, now on the *default* GH-write harness. ## Synthesis
## Synthesis — Round 2: GH-Write Broker, Home vs Headless

All three harnesses converge on the same structural finding despite different execution models: **the broker protocol is well-matched to headless/dispatched operation but under-specified for home/interactive operation**, and that gap is not cosmetic — it's a live bypass of the security model the design is meant to establish.

**Compatibility.** Claude, Codex, and Grok each confirm the request/result file mechanism itself works fine in headless mode — daemon-owned worktree, post-turn harvest, no protocol friction. But all three independently hit the same wall in home mode: the spec (§5/§6) assumes a dispatch daemon is present to run the post-turn hook or sidecar. Interactive sessions aren't dispatch-owned, so there's no guaranteed watcher to pick up the request file — Claude calls this an unstated scope question, Codex calls it a missing "registration/attachment path," Grok observes concretely that a home-mode write into an unregistered tree is "silently ignored (no result file)." Grok also flags a mechanical compatibility risk carried over from #342 (CWD not pinned to the registered worktree) that would independently break file discovery in headless mode too.

**Security.** This is where the panel is most aligned and most concerned. For headless, all three agree the broker is a clear improvement — token never touches the agent process, matching the design's intent. For home mode, the story inverts: Claude notes that without an explicit in-scope/out-of-scope statement, interactive Claude retains direct MCP/`gh` write access with its own identity — precisely the bypass §4 claims to close, just outside the clause's stated reach. Grok's finding is sharper: Grok already holds live `gh` and shell access with `can_gh_write=True` in both modes, and headless dispatch commonly runs with elevated auto-approve permissions — meaning Grok can skip the broker entirely today, landing on the same personal-identity/#569 exposure the broker was designed to eliminate, and that exposure is *worse*, not better, in home mode where there's no daemon oversight at all.

**Performance.** No material objection from anyone. Post-turn is near-zero overhead in all three harnesses (Claude: nothing extra; Codex: one broker startup + token mint + `gh` call, acceptable; Grok: cheap for headless, no-op for home). The one real caution is elevated/sidecar polling: Codex and Claude are fine with file-reread polling since their sandboxes handle it cheaply, but Grok flags that if the sidecar wait is implemented as *model-driven* tool-loop polling rather than a host-level blocking wait, a 60s bounded wait could burn a meaningful fraction of a turn's tool budget — this needs to be a single blocking host wait, not per-second tool calls.

**Decision:** Approve the broker design for headless/dispatched operation as specified, but do not merge or badge it as covering "home and headless" until the spec is amended with (1) an explicit statement of whether interactive/non-dispatched sessions are in-scope, and if so, a defined registration/attachment path so the request/result files are actually observed outside a dispatch daemon; (2) an explicit requirement that direct `gh`/MCP write access be denied or stripped in home mode for any harness capable of it (Grok in particular, given its default live `gh` access), closing the exact bypass the broker exists to prevent; and (3) a normative note that elevated-sidecar waits must be implemented as a single blocking host-side wait, not model-driven polling. These are scoping and enforcement gaps distinct from Round 1's protocol-hardening items, and they determine whether the broker is a universal write path or a headless-only one wearing a universal label.
