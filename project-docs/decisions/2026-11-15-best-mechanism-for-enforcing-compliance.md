Replacing static files with dynamic injection introduces cold-start vulnerabilities and bootstrap fragility.

For interactive sessions, the most reliable mechanism is periodic JIT re-injection at task boundaries, backed by the static instruction files. In my Codex behavior, a session-start file establishes the operating frame, but a long conversation, compaction, and shifting task scope can make those instructions less salient. A concise, task-specific context pack immediately before implementation, review, commit, or dispatch restores the relevant rules at the point of action. Tool-call-time checks are valuable as gates for high-risk operations, but too late as the primary compliance mechanism: they can prevent a bad write without ensuring the preceding reasoning followed the charter.

For headless dispatch, `generate_context()` and `synthesize_context_pack()` provide a substantially stronger baseline because every worker receives structured, task-scoped instructions. However, compliance can still degrade in a long-running job if the worker accumulates local context, encounters competing tool output, or crosses multiple task phases. The gap is best closed with phase-boundary refreshes—before implementation, verification, and handoff—and explicit machine-checkable gates such as `synlynk pr check`, policy checks, and required-file assertions.

JIT context packs should therefore become universal infrastructure, but not replace static files. Static files are the durable source of truth, discoverable by humans and harnesses and necessary for bootstrapping. JIT packs are the runtime delivery layer: compact, prioritized, and tailored to the current story and action. Replacing the source files would risk drift, incomplete startup context, and loss of repository-local discoverability.

Measurement is possible now, but existing data is insufficient by itself. `cost_entries` can show overhead, and `capability_ratings` can provide outcome signals, while `synlynk pr check` supplies concrete checklist compliance. To establish causality, synlynk needs instrumentation for mechanism variant, injection points, instruction violations, gate failures, rework, and task outcomes. A controlled A/B or stepped rollout—static-only versus JIT-at-boundary versus JIT-plus-gates—could measure compliance rate, escaped violations, rework, and cost.

My position: use static instructions as policy authority, JIT packs as universal runtime reinforcement, and tool/policy gates as enforcement backstops. Interactive sessions need boundary injection most urgently; headless sessions should add it to their already-strong generated prompt path.
