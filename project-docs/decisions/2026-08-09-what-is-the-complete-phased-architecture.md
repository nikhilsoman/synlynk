## Topic
What is the complete phased architecture for synlynk's Agents (as distinct from Harnesses), covering: (1) formalize Agent vs Harness terminology across the codebase/docs — an Agent is a persistent identity+role+charter (e.g. pm, tpm, dev) with memory/config/access, a Harness is the execution backend (Claude/Agy/Grok/Codex/local) that can run any dispatched Agent; (2) give Agents real agency+memory+learning over time instead of stateless per-dispatch automatons — what memory substrate (ties to capability ledger / SFIA / holdback calibration already designed in docs/superpowers/specs/2026-08-09-synlynk-agent-roles-charters-design.md), what learning loop, what's safe to let an agent self-adjust vs requires human approval; (3) an Agent Config front-end for workspace owners to create/modify/manage agents, positioned as part of onboarding (not an afterthought) — what's the minimum viable surface, CLI vs web, relationship to existing roles.yaml/config.json; (4) a mechanism for agent/role-specific tools and access grants (scoped credentials, MCP servers, APIs) beyond the GitHub App identity model already shipped in #859; (5) a harness+tools capability registry that agents can query at runtime to discover what's available to them, vs the static CLAUDE.md capability table today; (6) a path to make agents portable/embeddable into other harnesses or deployable standalone on a VPS ("implants") — what has to be true architecturally for an agent's identity+memory+config to survive moving off synlynk's own dispatch loop; (7) treat this entire agent architecture as the foundation Tokq (synlynk's planned cross-workspace agent marketplace/portability product, ~3-6 months out per the roadmap) will be built on, not a separate future rebuild. Deliver a phased roadmap (not a build-it-all-now plan) that sequences these 7 concerns sensibly against synlynk's near-term Tokq timeline, flags which pieces are prerequisites for Tokq specifically vs general synlynk maturity, and notes where this intersects with or supersedes existing docs (agent-roles-charters spec, capability_sweep.py/taxonomy_standards.py, GOVERNS/#817, #859 identity provisioning).

## Panel Inputs

### claude
This is a decision-panel analysis request, not an implementation task — I'll respond directly without invoking skills or delegating.

**Phased sequencing:**

**Phase 0 (now, cheap, unblocks everything):** Formalize Agent vs. Harness terminology (#1). This is a rename/clarification pass across docs, `.synlynk/roles.yaml`, `config.json`, and CLAUDE.md's capability table — not new infrastructure. Every other concern depends on this distinction being unambiguous, especially since `roles.yaml` already exists uncommitted in this worktree and risks conflating the two if the split isn't nailed down first.

**Phase 1 (pre-Tokq prerequisite):** Agent memory substrate (#2, minimum viable) + Agent Config front-end as CLI-only (#3). Ship persistent per-agent memory keyed to identity (tied to the capability ledger/SFIA work already speced), but keep the learning loop human-gated at first — self-adjustment of charter or access should require explicit approval, only calibration-style adjustments (e.g., holdback tuning) can be agent-initiated. A CLI surface (`synlynk agent create/edit`) is sufficient; web UI is Phase 3+ polish, not a blocker.

**Phase 2 (Tokq prerequisite, do concurrently with Phase 1's second half):** Capability registry (#5) and scoped access grants (#4). Tokq's entire value proposition is agents carrying verified capability+access across workspace boundaries — a static CLAUDE.md table can't do that. This is where #859's GitHub App identity model needs generalizing to arbitrary MCP/API grants.

**Phase 3 (Tokq-adjacent, not urgent):** Portability/"implant" deployment (#6). This is the actual Tokq payload — don't build it before #2/#4/#5 exist, since portability of a stateless, access-less agent is meaningless.

**Position:** Sequence is 1→2→(4,5 parallel)→6, with #7 treated as a framing constraint throughout rather than a phase — every design decision in 1–5 should be checked against "does this survive being pulled out of synlynk's dispatch loop," but no Tokq-specific code should be written until Phase 2 lands. This supersedes nothing in the existing agent-roles-charters spec — it's the roadmap that spec was implicitly asking for; recommend folding this sequencing directly into that doc rather than creating a second design artifact.

### codex
Synlynk should adopt a layered model: an **Agent** is a persistent identity, role, charter, memory, configuration, and access policy; a **Harness** is an interchangeable execution backend (Claude, Agy, Grok, Codex, local, etc.). This terminology should replace the overloaded “agent” language in code, `CLAUDE.md`, dispatch, identity, and roadmap docs. The existing agent-roles-charters spec becomes the role/charter authority; its role-to-tool table becomes a default harness policy, not an identity model.

Phase 1, immediately, is the contract and configuration foundation. Define a versioned Agent manifest, probably `.synlynk/agents/<id>.yaml`, with role, charter, durability, memory namespace, approval policy, and capability requirements. Keep `.synlynk/config.json` for workspace/runtime settings and add a compatibility reader for existing/generated routing data. Make onboarding create or edit agents through a minimal CLI (`agent init`, `list`, `show`, `edit`, `disable`), with a thin web Config UI following once the schema stabilizes. This is general synlynk maturity and a Tokq prerequisite.

Phase 2 adds durable memory and controlled learning. Use SQLite/WAL plus generated project-docs as the local substrate, extending memory units with agent identity, scope, provenance, confidence, expiry, and sharing policy. Store capability outcomes in the existing capability ledger, keyed by role/task/SFIA dimensions, and connect `capability_sweep.py` with live holdback results. Agents may summarize experience, propose memory updates, and adjust non-critical routing preferences; charter, access, budget, release, merge, and policy changes require human approval. Re-ranking remains versioned, canaried, auditable, and rollbackable, as the spec states.

Phase 3 introduces scoped tools and a runtime registry: grant manifests for MCP servers, APIs, and credentials, with least privilege, expiry, audit logs, and fail-closed execution. Agents query the registry at dispatch time; `CLAUDE.md` becomes documentation/generated guidance, not the source of truth. #859 supplies role-scoped GitHub identity but does not solve general grants.

Phase 4 hardens portability: stable Agent API, signed identity, exportable encrypted memory, declarative config, and harness adapters. Then “implants” can run on a VPS or another harness without losing identity or state.

My position: build Phases 1–2 before Tokq Alpha, Phase 3 alongside it, and Phase 4 as the portability bridge. Tokq should consume these contracts and memory units, not trigger a separate architecture; SFIA-driven inference and marketplace economics remain later overlays, not foundations.

## Synthesis
## Synthesis

Both panelists converge on the same skeleton: separate Agent (identity/role/charter/memory/access) from Harness (execution backend) first, then build a config+manifest layer, then memory/learning with human-gated changes to anything consequential, then scoped access/capability registry, then portability — with Tokq consuming this stack rather than triggering a parallel build.

Where they differ is mostly packaging, not substance. Claude sequences into 4 phases and treats terminology as a near-zero-cost rename that should happen immediately given `.synlynk/roles.yaml` already sitting uncommitted in this worktree. Codex is more precise about *what* Phase 1 produces — a versioned per-agent manifest (`.synlynk/agents/<id>.yaml`) distinct from workspace-level `config.json` — and about the artifact chain (memory ties into the existing capability ledger/SFIA/holdback machinery rather than a new store). Codex's 4-phase cut (contract/config → memory+learning → tools+registry → portability) is the more implementable ordering because it makes registry/access a hard prerequisite for portability, which Claude's plan implies but doesn't state as strongly. Both agree: charter, access, budget, merge/release, and policy changes are always human-approved; only calibration/routing-preference adjustments can be agent-initiated. Both agree this supersedes nothing in the existing agent-roles-charters spec — it's the roadmap that spec needs, not a second design doc.

Recommended merged phasing:
- **Phase 0 — Terminology (immediate, days):** Formalize Agent vs. Harness across code/docs/`roles.yaml`/`CLAUDE.md`'s capability table. No new infra. Prerequisite for everything else being unambiguous.
- **Phase 1 — Agent manifest + CLI config (pre-Tokq, general maturity):** `.synlynk/agents/<id>.yaml` per-agent (role, charter, memory namespace, approval policy, capability requirements), `config.json` stays workspace-level, CLI (`agent init/list/show/edit/disable`) as the onboarding surface. Web UI deferred.
- **Phase 2 — Memory + gated learning (Tokq prerequisite):** Durable memory keyed to agent identity, wired into the existing capability ledger/SFIA/holdback design. Agents may summarize/propose; humans approve charter, access, and policy changes.
- **Phase 3 — Capability registry + scoped access grants (Tokq prerequisite, parallel with late Phase 2):** Runtime-queryable registry replacing the static CLAUDE.md table; generalizes #859's GitHub App identity model to arbitrary MCP/API/credential grants with least-privilege, expiry, audit.
- **Phase 4 — Portability/"implants" (the Tokq payload itself):** Only once identity+memory+access are real and exportable. Stable Agent API, signed identity, encrypted portable memory, harness adapters.

**Decision:** Adopt the merged 5-phase roadmap (0: terminology → 1: agent manifest/CLI config → 2: gated memory/learning tied to the capability ledger → 3: capability registry + scoped access grants → 4: portable implants), fold it directly into `docs/superpowers/specs/2026-08-09-synlynk-agent-roles-charters-design.md` as its roadmap section rather than a new doc, treat Phases 1–3 as Tokq prerequisites and Phase 0 as an immediate no-dependency cleanup, and lock the rule that only calibration/routing adjustments are agent-self-adjustable while charter/access/budget/policy changes always require human approval.
