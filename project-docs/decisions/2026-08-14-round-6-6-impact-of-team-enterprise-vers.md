## Topic
ROUND 6/6 — Impact of Team/Enterprise versions; how to stabilize the entire "synlynk repo context" domain end-to-end (create → rotate/archive/refer/store/retrieve).

EVIDENCE — Rounds 1-5 have converged on a single design so far, all scoped to a SINGLE repo, single-writer-at-a-time reality:
- R1: hardcode project-docs/ at repo root as sole canonical namespace; project-docs/_generated/ subtree for state-derived output; no free-form project_docs_dir config; inventory-first, quarantine-preserving migration.
- R2: committed, versioned doc-lifecycle manifest as source of truth for classifying every doc path; synlynk audit-docs as continuous enforcement in CI/pr check/upgrade checkpoint; cc-videoreframing's pre-synlynk-migration/ archive pattern generalized.
- R3: standardize rca/archive/decisions/handoffs/brainstorm/blog under fixed docs/ paths via skill-injection (the only pattern proven to survive independent repo evolution); leave strategy/research/papers/reports repo-specific; replace failing 1:1 Blog Post Protocol with trigger-based release-communication workflow.
- R4: one unified manifest-driven CRUD contract for ALL doc types (generated + hand-maintained) with declared mutability, sole create_via path, automatic archive-not-delete, gitignore status DERIVED from manifest rather than set independently.
- R5: three-tier model (project-docs/ durable, project-docs/_generated/ projections, state.db operational truth); audit-docs --fix as idempotent backfill/reconciliation; ONE canonical instruction source with others as generated adapters; sentinel.md authority moves to state.db.

This entire design has been reasoned about as if each repo is a closed, single-operator system. But per CLAUDE.md's own project-standards and this project's actual trajectory: v0.9.2 already shipped `synlynk join` + team digest + write-arbitration + token budgets for multi-user team mode; the roadmap's v1.0.0 (GA, target Sep 2026) explicitly adds "Workgroup protocol · signed capability ledger"; v1.1.0 (Team Level, Q4 2026) adds "Relay → community server · cross-workgroup epics"; v1.2.0 (Enterprise, Q1 2027) adds "Cross-team · org-level governance agents." Team mode ALREADY exists today (project-docs/devlogs/<username>.md per-user, .synlynk_config.json mode: single|team) and this session found a LIVE bug caused by exactly this: two devlog files (nikhil.md 774 lines, nikhilsoman.md 418 lines) forked because of a username-identity mismatch — i.e., Team mode's per-user file-based sharding is ALREADY producing the same class of drift this whole brainstorm is trying to eliminate, just one dimension earlier (identity) than the doc-location dimension Rounds 1-5 addressed.

QUESTION: (1) Does the manifest-driven CRUD contract from Round 4 survive multi-writer team mode as-is, or does "sole create_via code path" need a concurrency/identity model bolted on — specifically, how should the manifest handle the devlog-per-username sharding bug (nikhil vs nikhilsoman) so that identity drift can't fork a doc category the same way location drift already has? (2) For v1.0.0's signed capability ledger and v1.1.0's relay-to-community-server: should the doc-lifecycle manifest itself become a signed, relayed artifact (so a Team/Enterprise workspace has ONE manifest across multiple synced local checkouts, not one per clone), and if so what's the minimal versioning/conflict-resolution primitive needed now in v0.13.x so that this doesn't require a breaking migration at v1.0.0? (3) For Enterprise's "org-level governance agents" (v1.2.0) — should audit-docs (Round 2/5) be designed now with an org-level rollup mode in mind (aggregating compliance across many repos' manifests), even though Enterprise is 5 months out, given that retrofitting cross-repo aggregation onto a single-repo-only audit tool historically has been costly (see this session's own project_docs_dir divergence as a cautionary precedent)? (4) Given all 6 rounds, what is the SINGLE highest-leverage next action for v0.13.x (not deferred to v1.0+) that would prevent 80% of the drift found in this brainstorm's investigation phase from recurring, given finite implementation bandwidth?

## Panel Inputs

### codex
The Round 4 CRUD contract survives team mode only if “sole create_via” means a single protocol, not merely a single local function. The protocol needs canonical identity resolution before path selection. Each user should have a stable workspace identity (preferably a configured UUID or signed capability subject), with normalized username aliases such as `nikhil -> nikhilsoman`. Devlog paths must be derived from that identity, never from arbitrary runtime usernames. The manifest should declare the canonical identity, aliases, and migration status; `audit-docs --fix` should merge/quarantine forked files deterministically, preserve provenance, and reject new aliases unless explicitly registered. This prevents identity drift from recreating location drift.

The manifest should become a relayed, signed workspace artifact eventually, but v0.13.x should avoid making signatures a prerequisite for CRUD. Add forward-compatible fields now: `workspace_id`, stable `manifest_id`, schema version, monotonically increasing revision, parent revision/hash, and actor identity. Use optimistic concurrency: writes include the revision they read; stale writes produce a conflict artifact rather than silently overwriting. This is sufficient for the current single-writer-at-a-time model and can later be wrapped in signed capability and relay protocols without migration. CRDTs are unnecessary at this stage.

For Enterprise, design audit output as a stable, machine-readable compliance snapshot keyed by workspace/repo/manifest revision. Do not build org aggregation yet; make rollup possible by ensuring each repo emits the same schema, status vocabulary, and provenance. An org agent can aggregate snapshots later without reverse-engineering local audit behavior.

The highest-leverage v0.13.x action is to implement canonical identity plus manifest-driven reconciliation as one end-to-end vertical slice: devlog alias detection/merge, `audit-docs --fix`, revision-aware writes, and CI enforcement. This directly addresses the live fork, hardens the CRUD contract, and establishes the compatibility seam for signed multi-checkout manifests and future org rollups.

### grok
I’ll ground this in the existing team-mode, identity, and lifecycle artifacts so the recommendation isn’t just abstract architecture.The Round 4 contract survives **as the policy layer**, not as the writer model. `create_via` names the only legal *operation*; it does not name the *subject*. Team mode already shards `project-docs/devlogs/<username>.md` off an unstable resolver (`get_username()`: `gh api user.login` first, then `git config user.name` slugged). That is why `nikhil.md` (774 lines) and `nikhilsoman.md` (418 lines) forked: two slugs, one human, no registry. The manifest must add a **sharded** category: `path_template`, `shard_key=member_id`, `members[]` as the only legal shards, `create_via=synlynk join`. `join` is the sole mint of a member + their devlog. All later writes resolve `member_id` through that table, never through live `gh`/`git`. Unregistered slugs fail `audit-docs` as identity-fork; aliases merge, they do not spawn a second file. Git `merge=union` stays the concurrency primitive; do not invent file locks in v0.13.x.

Do **not** sign or relay the lifecycle manifest. It is committed policy, same as `.gitattributes`. Git already gives every clone one copy. Relaying it would recreate the `project_docs_dir` split: local committed vs remote signed. What v1.0 signs is the **capability ledger** and later governance attestations. The only now-cost that avoids a v1.0 break: `schema_version`, stable `category_id`s, additive-only fields, and a `members[]` block. No CRDT, no signed blob.

Do **not** build org rollup. Do emit **stable machine-readable audit records** (`repo_id`, `schema_version`, `category_id`, `violation_code`). That is the cheap hinge. A prose-only auditor is what made `project_docs_dir` expensive to aggregate later.

**Position:** ship the committed lifecycle manifest plus an identity registry and make `audit-docs` fail on location drift *and* identity forks. That is the 80% move: it closes the live `nikhil`/`nikhilsoman` bug, enforces Rounds 1–5 in CI, and leaves a versioned schema so Team/Enterprise can later sign ledgers and roll up violations without a second migration.

## Synthesis
The manifest-driven CRUD contract survives team mode, but only as a protocol: `create_via` must govern identity resolution, authorization, path derivation, and writes—not merely select a local function. Devlogs should be declared as a sharded category keyed by a stable `member_id`, with an explicit identity registry and aliases. `nikhil` and `nikhilsoman` must resolve to one registered identity; unregistered or ambiguous identities must fail loudly, while `audit-docs --fix` merges or quarantines the fork with provenance preserved. Runtime GitHub or Git usernames must never directly determine filenames.

The lifecycle manifest should remain a committed workspace policy artifact, not become signed or relayed in v0.13.x. Git already provides clone-wide distribution, and signing the manifest now would create competing authority between local policy and future relay infrastructure. Add forward-compatible fields now: stable `manifest_id`, schema version, category IDs, workspace/repo identity, revision, parent revision/hash, actor/member identity, and additive sharding metadata. Writes should detect stale revisions and produce conflict artifacts rather than silently overwrite. Full signatures belong to the v1.0 capability ledger; CRDTs and a new relay protocol are unnecessary now.

`audit-docs` should not implement organization-wide aggregation yet. It should emit stable machine-readable audit snapshots with consistent schema, repository/workspace identity, manifest revision, category IDs, violation codes, status vocabulary, and provenance. That gives future governance agents a reliable rollup seam without prematurely coupling the single-repo auditor to Enterprise infrastructure.

Decision: In v0.13.x, implement one end-to-end vertical slice consisting of a committed manifest identity registry, canonical member-ID devlog paths, alias/fork detection and provenance-preserving reconciliation through `audit-docs --fix`, revision-aware writes, and stable machine-readable audit output enforced in CI and `pr check`. Keep the manifest unsigned and non-relayed for now, but make its schema forward-compatible with signed capabilities and cross-repo rollups. This is the highest-leverage action because it closes the live identity fork while simultaneously hardening location, concurrency, Team, and future Enterprise integration points.
