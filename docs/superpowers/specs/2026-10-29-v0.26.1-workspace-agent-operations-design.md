# v0.26.1 — Workspace-agent charter and role operations Design Specification

## 1. Intent & Context

Following the release of `v0.26.0` (commit `6266b58d`, PR #2620), milestone `v0.26.1` addresses the core operational contracts of Synlynk's multi-agent fleet: **Workspace-agent charter and role operations**.

As specified in the canonical execution schedule and roadmap:
> "Daily stable gate: workspace-agent charters, authority, SOPs and GOVERNS adherence are signed off and exercised; address #2305 where needed for enforceable role procedures. Parent #2458; release epic #2469; goals goal-eacab0dc, goal-a222b393, goal-06758149."

Synlynk operates a multi-agent orchestration fleet spanning four execution harnesses (`claude`, `agy`, `codex`, `grok`) and distinct organizational roles (`pm`, `architect`, `dev`, `qa`, `tpm`, `maintainer`). While v0.26.0 stabilized the runtime and daemon substrate, five structural gaps in workspace-agent operations remain:
1. **Disconnected Charter Schemas (#2305):** JSON charters in `.synlynk/charters/*.json` are isolated dead weight used only for drift detection, while Markdown frontmatter in `.synlynk/agents/` / `agent_store.py` lacks enforceable execution contracts, tools, and verification gates.
2. **Missing Headless Skill Enforcement:** Interactive agents receive superpowers hooks, but headless dispatches receive inert YAML lists with zero binding execution prompts or post-flight verification.
3. **Unexercised Maintainer Loop (story-2e48a8c5):** Sentinel alerts are compacted via `compact_sentinel_alerts()`, but lack an autonomous Maintainer wake-cycle to triage, correlate, and file reproduction issues.
4. **Outdated Single-Harness PM Assumptions (#2488):** Documentation still assumes Claude is the sole Home Conductor, despite empirical proof across v0.25.5–v0.26.0 that Agy, Codex, and Grok operate successfully in Mode A.
5. **Dispatch & Worktree Race Hazards:** Collisions in cross-harness claims (#2511), stale dispatch worktrees (#2185), capacity gate regex matching (#2233), and AST context over-inflation (#2133).

This specification establishes the architectural blueprints, schema unifications, runtime contracts, and verification suites for `v0.26.1`.

## 3. Workstream 1: Charter Schema Convergence & Superpowers Binding (gh:#2305)

### Problem Statement
`synlynk/charters.py` manages an `AgentCharter` dataclass that serializes to `.synlynk/charters/<role>.json`. This is only used for drift detection and never read during prompt assembly. Conversely, `synlynk/charter_schema.py` and `synlynk/charter_injection.py` parse YAML frontmatter from `.synlynk/agents/`, but ignore `autonomous_authorities`, `escalation_triggers`, and `wake_cycle_sop`, and treat bound skills as passive metadata without prompt enforcement.

### Architectural Solution
1. **Retire `.synlynk/charters/*.json`:**
   - Migrate existing `.json` metadata into the canonical Markdown frontmatter in `synlynk/charter_schema.py` and `.synlynk/agents/`.
   - Update `synlynk/charters.py` (`drift_status`, `adapt`, `validate_charter`) to parse and adapt Markdown frontmatter directly.
2. **Unified Frontmatter Schema:**
   The canonical frontmatter schema expands to support:
   ```yaml
   ---
   schema_version: "2.0"
   role: "maintainer"
   description: "Autonomous repository hygiene, alert triage, and issue reproduction"
   durability: "durable"
   mandate: "Maintain substrate health, triage sentinel faults, and eliminate test flakiness"
   autonomous_authorities:
     - "triage_sentinel_alerts"
     - "file_reproduction_issues"
     - "probe_scratch_worktree"
   escalation_triggers:
     - "recurring_sev1_fault"
     - "budget_exceeded"
     - "unresolvable_merge_conflict"
   skills:
     - "test-driven-development"
     - "systematic-debugging"
   sops:
     - "wake_cycle: read sentinel -> deduplicate -> probe -> file issue"
   tools:
     - "pytest"
     - "git"
     - "gh"
   credentials:
     - "github_app:synlynk-maintainer"
   verification_contracts:
     - "mandatory_reproduction_test"
     - "clean_exit_receipt"
   ---
   ```
3. **Superpowers Skill Binding (Option 2B Implementation):**
   - **In-Flight Prompt Gate (`synlynk/charter_injection.py`):**
     When `skills` lists `test-driven-development`, `systematic-debugging`, or `brainstorming`, the injector injects the exact non-negotiable operational instructions into the dispatch prompt:
     ```
     [MANDATORY SKILL CONTRACT: test-driven-development]
     You MUST implement changes following strict TDD:
     1. Author a reproduction/verification test first.
     2. Verify test failure on baseline.
     3. Implement the minimal fix.
     4. Verify test success and lack of regressions.
     Commits that add code without accompanying tests violate this contract.
     ```
   - **Post-Flight Verification Gate (`synlynk/jobs.py`):**
     When reconciling a completed job, if `verification_contracts` mandates test evidence:
     - Verify that the target branch/commit modified files in `tests/` or executed `pytest`.
     - Flag missing verification with `FAILED_VERIFICATION` and require attestation remediation before review dispatch.

## 4. Workstream 2: Autonomous Maintainer Role Charter & Sentinel Maintenance Loop (story-2e48a8c5)

### Problem Statement
In v0.26.0, `compact_sentinel_alerts()` was shipped to prune aged alerts and consolidate recurring failures in `.synlynk/sentinel.md`. However, sentinel alerts remain passive logs. There is no active agent process assigned to triage these alerts, identify regressions, or author reproduction tests.

### Architectural Solution
1. **Maintainer Charter Definition:**
   - Formalize `.synlynk/agents/maintainer.yaml` (and role slug `maintainer`) with the expanded 2.0 schema.
2. **Sentinel Triage Engine (`synlynk/maintainer.py`):**
   - Implements `triage_sentinel_alerts(max_age_days=7)`:
     - Parses structured alerts from `.synlynk/sentinel.md`.
     - Groups alerts by `fingerprint` (subsystem + error signature).
     - Computes occurrence frequency, last-seen timestamp, and affected worktree/branch.
   - Implements `generate_triage_issue(fingerprint, occurrences)`:
     - Extracts the canonical traceback and stack frames.
     - Generates a standalone reproduction script or command (e.g. `pytest tests/test_... -k ...`).
     - Formats issue body leading with Intent, Context, Reproduction Recipe, and Impact.
3. **Autonomy Pass Integration (`synlynk/daemon.py` / `synlynk/watch.py`):**
   - In `_autonomy_pass()`, if active alerts exceed threshold ($N \ge 3$ recurring instances over 24h) and no open issue exists with matching title/fingerprint:
     - Route issue creation to `codex` per GitHub write priority (#426) via `gh issue create --label maintainer-triage`.
4. **Maintainer CLI Surface:**
   - `synlynk maintainer triage`: Prints summary of active recurring alerts and triage suggestions.
   - `synlynk maintainer probe --alert <id>`: Launches a sandboxed scratch worktree to execute the reproduction recipe and verify whether the fault reproduces on `origin/main`.

## 5. Workstream 3: Multi-Harness Interactive Home Conductor PM Authorization (gh:#2488 / story-743e91fe)

### Problem Statement
`CLAUDE.md`, `GEMINI.md`, and `AGENTS.md` historically defined Claude as the sole PM / Home Conductor, treating non-Claude interactive leadership as unverified. Empirical evidence across v0.25.5, v0.25.6, and v0.26.0 demonstrated that Agy (Gemini) successfully drove end-to-end releases as Mode A Conductor under strict non-author review.

### Architectural Solution
1. **Formally Authorize Quad-Harness Mode A Conductors:**
   - Update `CLAUDE.md`, `GEMINI.md`, `AGENTS.md`, and `.synlynk/policy.json` (`conductor_authority`).
   - Define Mode A Conductor capabilities for all four harnesses: `claude`, `agy`, `codex`, `grok`.
2. **Preserve Invariant 1 (Strict Non-Author Review):**
   - The Home Conductor harness must NEVER review or merge its own PRs.
   - If Agy is Conductor and authors feature code, review MUST be dispatched to Claude or Codex.
   - If Claude is Conductor and authors feature code, review MUST be dispatched to QA (Agy or Codex).
3. **Dynamic EV Routing & Capability Calibration:**
   - Home Conductors select dispatch targets dynamically using `synlynk capability select` or `capability_ratings` from `state.db`.
   - GitHub write operations remain pinned to Codex by default per #426.

## 6. Workstream 4: Dispatch Preflight & Worktree Hardening

### Problem Statement
Parallel headless dispatches encounter subtle edge-case friction:
- #2511: Cross-harness home claim collisions when multiple interactive sessions run concurrently.
- #2185: Worktree and branch collisions caused by dangling scratch artifacts from killed jobs.
- #2233: Capacity gate regex checking false-matching prompt substrings instead of `--task-type`.
- #2133: AST context packaging walking entire worktree directories instead of task-scoped subsets.

### Architectural Solution
1. **Shared Claim Locking (#2511):**
   - Move claim persistence from checkout-local `.synlynk/active_claims.json` to atomic locks in SQLite `state.db` or a canonical filesystem lock in `~/.synlynk/claims/`.
2. **Worktree Preflight Pruning (#2185):**
   - In `synlynk/dispatch.py::_prepare_worktree()`, before creating a branch or worktree, verify if an orphaned directory exists in `.worktrees/`. If owned by a dead PID, prune cleanly via `git worktree remove --force`.
3. **Structured Task-Type Capacity Gate (#2233):**
   - Enforce capacity reservation checks against the explicit `--task-type` flag (`review`, `implement`, `triage`, `deploy`) rather than heuristic prompt regexes.
4. **Scoped Context Assembly (#2133):**
   - Enforce path-scoped file list generation in `synlynk/context.py`, preventing full AST traversal when dispatching small unit tasks.

## 7. Workstream 5: Google Research Harness² Architecture Incorporation

### Problem Statement
Google Research’s Harness² (*Empirical Foundations of Self-Improving Agent Architectures*, arXiv:2610.14224) establishes the formal 8-component tuple governing autonomous agent platforms and the dual-recursion *Propose-Probe-Compose* paradigm. Synlynk’s architecture implements these concepts across disparate modules without formal unified mapping.

### Architectural Solution
1. **Architectural Mapping Document (`docs/architecture/harness-squared-mapping.md`):**
   Formally document how Synlynk’s subsystems map to the Harness² 8-component specification:
   - **$H_{cfg}$ (Harness Config):** `.synlynk/config.json`, `.synlynk/policy.json`, role permissions.
   - **$A_{rt}$ (Agent Runtime):** `synlynk/dispatch.py`, harness subprocess pipes (`claude`, `agy`, `codex`, `grok`).
   - **$E_{sbx}$ (Environment Sandbox):** Git worktrees (`.worktrees/`), sandbox isolation, port hunters.
   - **$T_{spec}$ (Task Specification):** Story definitions in `state.db`, GitHub issue specs, frontmatter briefs.
   - **$C_{asm}$ (Context Assembly):** `synlynk/context.py`, AST token pruners, charter injectors.
   - **$V_{har}$ (Verification Harness):** `synlynk pr check`, `pytest` runner, invariant verification oracles.
   - **$M_{eng}$ (Mutation Engine):** Git commit/patch application, charter adapt engine (`synlynk charters adapt`).
   - **$T_{trk}$ (Telemetry Tracker):** `synlynk/costs.py`, `state.db`, `sentinel.md`, `capability_ratings`.
2. **Targeted Charter Evolution (Propose-Probe-Compose):**
   - **Propose:** An agent or Conductor proposes charter adjustments (e.g. updating `behavioral_weights` or adding an escalation trigger) based on cost/error logs.
   - **Probe:** The mutation is validated in a scratch sandbox against existing charter validation suites (`validate_charter`, test dispatch prompt injection).
   - **Compose:** Validated charter updates are committed to `.synlynk/agents/<role>.yaml`.

## 8. Verification & Test Strategy

1. **Unit & Contract Tests:**
   - `tests/test_charter_schema.py`: Test expanded YAML frontmatter parser, validation rules, required keys, and error diagnostics.
   - `tests/test_charters.py`: Verify migration from JSON to Markdown, drift detection, and `synlynk charters adapt` without `.json` dependencies.
   - `tests/test_charter_injection.py`: Verify that bound superpowers skills render mandatory enforcement language into prompt headers.
   - `tests/test_maintainer.py`: Test sentinel alert parsing, deduplication, fingerprinting, and reproduction issue generation.
   - `tests/test_dispatch_preflight_hardening.py`: Test worktree collision recovery, task-type capacity checks, and scoped context generation.
2. **Integration Verification:**
   - Execute live `synlynk charters drift` and `synlynk charters check` across all registered roles (`dev`, `qa`, `pm`, `architect`, `tpm`, `maintainer`).
   - Verify Maintainer triage execution against synthesized sentinel alerts in a temporary workspace.
   - End-to-end regression run across the full Synlynk test suite (~5,100+ tests).
