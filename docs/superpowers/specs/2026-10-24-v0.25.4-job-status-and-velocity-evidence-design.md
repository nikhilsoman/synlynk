# v0.25.4 — Accurate job status and completion evidence

**Date:** 2026-10-24
**Status:** Draft, pending approval
**Release target:** 2026-10-25
**Parent:** #2458 · Release epic: #2467 · Goals: goal-079e2f37, goal-9ef9a965, goal-eacab0dc

## Problem

synlynk's job telemetry is trusted without independent verification at multiple
points in the same loop:

```
dispatch allocation (capability_sweep.py / policy.json routing)
        │
        ▼
  job execution
        │
        ▼
  status / gh-write-effect verification   <-- Workstream A
        │
        ▼
  cost / telemetry attribution (cost_entries, capability_ratings)  <-- Workstream B, C
        │
        ▼
  capability_ratings aggregates feed back into routing  <-- Workstream E (boundary only)
```

Two live 2026-10-24 incidents from the v0.25.3 release session are the concrete
regression fixtures for this release:

- `job-cbe2a362` (Grok, reviewing/merging PR #2577): labeled
  `succeeded_gh_write_failed`, but `gh pr view 2577` confirms a clean merge
  (commit `e86d17c2`, `APPROVED`). The job's own transcript already printed
  the correct `gh pr view`/merge output.
- `job-77e59e43` (Codex, implementing gh:#2576): labeled
  `succeeded_gh_write_failed` / `FAILED_NOOP_DENIED` with "Expected GitHub
  effect was not verified directly via gh" — but it had genuinely opened PR
  #2579 with the right scoped diff, also visible in its own transcript.

This release closes the gap between what a job's own transcript already shows
and what the status/oracle layer reports, and extends the same discipline one
step upstream (attribution) and one step downstream (the routing decisions
that already consume attribution data).

## Workstream B — telemetry attribution mismatch (#2547 "role/model mismatches")

`cost_entries.harness` / `.agent` / `.agent_role` / `.model` are free columns
populated independently of the authoritative `daemon_jobs.actual_harness` /
`.resolved_model` (`synlynk/db.py:1851-1880`, `synlynk/db_schema.py:216-222`).
Divergence is most likely for:
- handoff jobs (`daemon_jobs.previous_agents` / `.handoff_count` > 0), where a
  `cost_entries` row may still carry the harness from dispatch time, not
  settlement time
- manually backfilled rows (Cost Capture Protocol's `synlynk cost log`
  backfill path), where a human/PM session infers harness/model from logs

**Fix:** at write time (`_ensure_daemon_job_cost_entry` and the `cost log` CLI
path), cross-check the row being written against the settled `daemon_jobs`
row for the same `job_id`. On mismatch: refuse the write and surface the
conflicting values (don't silently coerce — a human backfill may have
information the settled row lacks, e.g. the no-provenance case already
documented in CLAUDE.md's Cost Capture Protocol).

**Historical audit:** a one-time report (not a migration, not a silent
rewrite) listing existing `cost_entries` rows whose `harness`/`model` disagree
with their `daemon_jobs` row, for manual review.

## Workstream C — post-job structured metric extraction

New table `job_timing_metrics`:

| column | source |
|---|---|
| `job_id` | FK to `daemon_jobs` |
| `harness`, `model`, `role` | from settled `daemon_jobs` (post Workstream B fix) |
| `mode` | `home` \| `headless` |
| `queue_seconds` | `started_at - enqueued_at` |
| `active_seconds` | `completed_at - started_at` |
| `ci_review_seconds` | from `gh pr view --json` timeline, when `gh_write_target` is a PR |
| `human_wait_seconds` | gap(s) with no job/CI activity, from Sentinel/job records |
| `self_reported_json` | raw structured block from the job's own final transcript output, if present |
| `cross_check_status` | `agree` \| `disagree` \| `absent` — self-report vs. objective columns |

Populated by a hook at the same choke point as `_settle_daemon_job_terminal`
(Option A from brainstorm discussion). Self-report (Option C) is parsed but
**never substituted** for the objective timestamp-derived columns — it is
stored for comparison only, consistent with this release's "don't trust a
label without independent verification" theme.

## Workstream E — capability-sweep boundary (audit + guard only)

Scope is deliberately narrow: synlynk inherits `capability_sweep.py`'s
*outputs* at the routing boundary; the sweep's own effectiveness/mechanics are
upstream harness/model control-plane work, out of scope here.

- **E1 (audit):** re-run the query behind the current
  `_GH_WRITE_HARNESS_PRIORITY` ordering (`codex 9.04 n=410`, etc., in
  CLAUDE.md) against Workstream B's mismatch-audit output. If any backing
  sample is flagged mismatched, note it explicitly — do not silently leave a
  possibly-wrong ordering in CLAUDE.md/`policy.json`.
- **E2 (guard):** confirm `capability_sweep.py`'s baseline-seed-when-empty
  path (`synlynk/capability_sweep.py:545`) cannot be mistaken for a harness
  having real calibration data — i.e. it must be distinguishable from a
  genuine n≥5 measurement, so a seeded baseline can't masquerade as
  measured allocation evidence (directly relevant to Muse's
  calibration-blocked status in the roadmap).

No changes to sweep logic, scoring, or allocation algorithms themselves.
