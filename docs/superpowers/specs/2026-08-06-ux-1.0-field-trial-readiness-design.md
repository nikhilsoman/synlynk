# UX 1.0 Field Trial Readiness — Design

**Status:** Draft, pending user review
**Author:** Claude (PM/design), for dispatch to Codex/Grok/Agy
**Related:** `docs/superpowers/specs/2026-08-05-synlynk-ux-1.0-design.md` (the shipped TUI/Vizor/uxcore/Slack work, PR #731), `docs/blog/99-pr731-synlynk-ux-1.0-tui-vizor-uxcore.md`, `docs/superpowers/specs/2026-08-08-governs-lifecycle-workspace-agent-pilot-design.md` (owns the shared terminal-tip nudge mechanism this spec's Phase 3a depends on)

## Context

PR #731 shipped the 3 UX surfaces — TUI (`synlynk/tui.py`), Vizor web HUD (`synlynk/viz.py`), and the Slack/BYOUX notifier (`synlynk/notifiers/slack.py`) — all sitting on the shared `synlynk/uxcore.py` library (Actor/Role RBAC seams, read accessors, single write chokepoint, capability manifest, feature flags, `subscribe()` event tailing). PR #746 added the retrospective blog post. Both are merged to `main`.

Before cutting a Named Release, the user paused to insert a field-trial readiness phase: validate all 3 surfaces against real production workflows, build a visual journey-map artifact matching the fidelity of an existing reference prototype, embed live in-context nudges toward the new surfaces during normal dispatch work, and only then run a 1–2 week field trial across all 4 active projects before going live.

This spec covers that readiness phase as 4 ordered work packages within one release-readiness effort — not 4 independent subsystems. They share one dependency chain (Phase 1 + Phase 3 gate Phase 4; Phase 2 runs in parallel) and one release goal, so they're specified and planned together, then dispatched as separately-scoped tasks per the repo's capability-based routing.

**Reference artifact for Phase 2:** `~/dev/rxcc/docs/brainstorm/ux-redesign/final-prototype.html` — a single-file interactive HTML "Unified Device & Journey Simulator" with a device-mode toggle (Desktop Web / iOS Safari / Android Chrome), Tailwind CDN + Google Fonts styling, and animated device-frame transitions. This spec adapts that pattern from *device* to *surface* (TUI / Vizor / Slack).

## Phase 1: Surface Test Plan

**Goal:** Every interactive element on all 3 surfaces verified against real dispatch workflows on all 4 active projects (rxcc, cc-videoreframing, playblazer-ng, synlynk-on-itself), with evidence — not vibes.

**Deliverable:** `docs/superpowers/ux-1.0-surface-checklist.md` — a durable, reusable checklist (not a throwaway), structured as one section per surface:

- **TUI (`synlynk/tui.py`):** every curses panel, every keybinding, launched against a project with active jobs. Checklist items enumerate concrete panels/actions (job list, job detail, approve/kill keys, RBAC-denied states, empty states).
- **Vizor (`synlynk/viz.py`):** every HTTP route, every UI action (dispatch form, job list/detail, approve/kill buttons, capability-manifest-gated controls, `subscribe()`-driven live updates).
- **Slack notifier (`synlynk/notifiers/slack.py`):** every message type the notifier sends (job started, job completed, job failed, approval-needed), verified against a real Slack webhook.

Each checklist item gets a pass/fail column plus an evidence pointer (screenshot path or log excerpt) and the project it was verified against. An item isn't checked off until it's been exercised on at least one real project with a real dispatch job — synthetic/staged runs don't count as verification for this checklist (though they're fine for initial dry-runs).

**Verification approach:** manual, self-verified now (not an automated framework) — matches the project's standing practice of independently verifying dispatched work rather than trusting job status alone. A follow-up ticket is filed (not a blocker for this phase or the trial) proposing an automated smoke-test suite (headless curses driver for TUI, HTTP client for Vizor, webhook mock for Slack) once the surfaces have stabilized through real field use — automating tests against a UI still expected to change from field feedback would mean rewriting the suite mid-trial.

**Ownership:** Claude runs this checklist directly (it's verification/PM work, not implementation) across all 4 projects. Any bugs found get filed as issues and routed to the appropriate implementer agent per the capability table; the checklist itself isn't "done" until every item is checked off clean, defects and all.

## Phase 2: Journey Map Simulator

**Goal:** An interactive, single-file HTML artifact visualizing each user-journey element per surface, at the same fidelity as the rxcc reference prototype.

**Deliverable:** `docs/brainstorm/ux-journey-map/` containing:
- `index.html` — landing page linking to each journey (per the brainstorming/visual companion pattern: content lives in `docs/brainstorm/`, not `.superpowers/` which is gitignored/ephemeral)
- `journey-map.html` — the simulator itself

**Architecture (Approach A — data-driven single template):** One HTML shell (nav, surface-toggle, shared CSS/animation) driven by a JS array of journey → step → per-surface-render objects. Adding a journey later means appending to the data array, not writing new page markup — this keeps the artifact maintainable as a living reference past the initial release, and mirrors how the rxcc reference itself structures its device-toggle pattern (just swapping "device" for "surface").

**Per-surface mockup rendering:**
- TUI steps render as styled `<pre>` blocks mimicking curses panel output (no real screenshot capture needed — hand-authored ASCII/box-drawing mockups keyed to what the actual panels render).
- Vizor steps render as simplified HTML/CSS mockups matching the real routes (dispatch form, job list, approve/kill controls).
- Slack steps render as styled message-bubble mockups matching the real BYOUX notifier payload format.

**Fidelity bar:** Tailwind CDN, a deliberate display/body font pairing (following this project's own design conventions, not copying rxcc's exact palette — the artifact-design principle of grounding choices in the subject, not templating), animated transitions on surface-switch, and "advisory pill" style callouts for contextual tips — content and journeys fully synlynk-specific.

**Journey groups, in on-page order (7 groups; confirmed with user, ordered for first-time users):**

1. **Install / upgrade / migrate** *(opens the simulator)* — `install.sh` on a fresh machine, `synlynk upgrade`, `synlynk init`/migrate on an existing repo, a version bump.
2. **synlynk concepts** — polyglot agent orchestration (Codex/Grok/Agy/Claude under one dispatch layer) and the context bridge at 3 levels: human→agent, agent→agent, agent→project/repo.
3. **Repo onboarding** — monorepo vs. multi-repo/worktree setups.
4. **SDLC-stage governance** — one sub-journey per gate in this repo's own Brainstorm/Spec → Plan → Build/Dispatch → Review → Deploy sequence, each shown across all 3 surfaces.
5. **Dispatch a task** — from "I have work to hand off" through agent/context-mode selection to seeing it running, across TUI/Vizor/the resulting Slack notification.
6. **Approve / kill a running job** — the RBAC/actor-seam write path: who can approve/kill, what each surface shows for pending-approval or in-flight jobs.
7. **Get notified & react** — the BYOUX consumer journey: a Slack message arrives via `uxcore.subscribe()`, user clicks through to Vizor or TUI for full context and action.

**Deliverable note:** this is a documentation/onboarding artifact, not a running app. It ships to `docs/brainstorm/`, committed in this feature's branch, and gets referenced from the eventual release's blog post. It runs on a parallel track — it does not block the field trial from starting (see Phase 4).

## Phase 3: In-Context Nudges

**Goal:** Turn ordinary dispatch work into passive onboarding by surfacing contextual, distinctive nudges toward underused UX surfaces — with a durable, user-controlled way to keep seeing (or fully silence) them.

**Reconciled with `docs/superpowers/specs/2026-08-08-governs-lifecycle-workspace-agent-pilot-design.md` (2026-08-08):** that spec's Section 4 builds the shared nudge mechanism — the distinctive terminal-tip presentation (fenced box, forced accept/close/follow), the `~/.synlynk/config.json` `nudges` block, and `synlynk config nudges off/on/reset` — as infrastructure its pilot workspace agent needs regardless of this spec. This spec does not rebuild that mechanism; it is the *second producer* into the same pipeline. Phase 3a below is scoped down accordingly: the terminal-tip delivery mechanism itself is built once, by the GOVERNS/workspace-agent-pilot plan; this spec's Phase 3a work is the UX-1.0-specific *content* (which surfaces are underused, per-surface tip copy) plugged into that already-existing mechanism.

**Rollout, phased (each independently dispatchable):**

- **3a — Terminal tips (UX-1.0-specific content, depends on the shared mechanism above).** Once the shared terminal-tip mechanism exists (built by the GOVERNS/workspace-agent-pilot plan), add a UX-1.0 tip producer: a frequency/novelty heuristic over telemetry state that emits tips like "3 jobs running — watch them live: `synlynk tui`", preferring surfaces the user's `state.db` shows no evidence of using — don't repeat the same tip within N invocations. *(Capability routing: CLI-plumbing → Codex.)*
- **3b — Vizor first-visit banner.** On Vizor's first HTTP request from a session (or after N days dormant), inject a dismissible banner pointing at an underused feature computed from that project's job history (e.g., "You've dispatched 12 jobs but never used approve/kill — try it"). *(Capability routing: Vizor HTTP+JS surface → Grok.)*
- **3c — Slack cross-links.** Extend `synlynk/notifiers/slack.py`'s message payload so job-completion messages include a "View live in Vizor" / "Open TUI" link/button. *(Capability routing: CLI-plumbing → Codex.)*

**Distinctive presentation (required, not optional):**
- **Terminal (3a):** wrapped in a visually distinct fenced box (box-drawing border, a marker glyph) — cannot be mistaken for a normal log line.
- **Vizor (3b):** a colored, animated toast/banner using an accent color distinct from the rest of the UI, a subtle slide-in transition — not a passive auto-dismissing banner.
- **Both require an explicit action** to clear: **Accept** (navigate to the surface), **Close** (dismiss this specific nudge), or **Follow** (open a linked doc). No silent timeout-dismiss.

**Persistent, user-controlled opt-out and replay:**
- New `nudges` block in the user-level config (`~/.synlynk/config.json`, alongside existing budget limits): `{"nudges": {"enabled": true, "dismissed_ids": [...], "last_shown": {...}}}`.
- `synlynk config nudges off` / `synlynk config nudges on` — toggles the whole feature.
- Closing an individual nudge marks only that nudge dismissed (added to `dismissed_ids`) — it won't repeat that exact tip, but other/new nudges can still surface.
- `synlynk config nudges reset` — clears `dismissed_ids`, letting all nudges resurface. This is the explicit "rerun nudges" mechanism requested — a user who wants a refresher (e.g., after a long gap, or a new surface ships) runs this instead of waiting for novelty heuristics to naturally re-trigger something.

**Test coverage:** each of 3a/3b/3c gets unit tests for the gating logic (novelty heuristic, dismissed-id suppression, config on/off) as part of its own dispatched task — this is standard implementation-task scope, not part of Phase 1's manual checklist.

## Phase 4: Field Trial & Release Plan

**Gate to start the trial:**
- Phase 1 checklist fully passed (every item checked off clean across all 4 projects), **and**
- Phase 3 nudges (3a/3b/3c) shipped and merged — 3a requires the shared terminal-tip mechanism from the GOVERNS/workspace-agent-pilot plan to have landed first.
- Phase 2 (journey simulator) is *not* a gate — it finishes in parallel during the trial window, since it's a documentation/onboarding artifact the trial doesn't depend on to run.

**Trial window:** 1–2 weeks minimum, all 4 active projects as live subjects (rxcc, cc-videoreframing, playblazer-ng, synlynk-on-itself), using a freshly-cut pipx install of `synlynk` at trial start — not the stale `0.13.0` build currently installed, which predates all of this work and doesn't reflect it.

**Exit criteria (both required):**
- **Bug bar (hard gate):** zero Sev1/Sev2 live issues opened against the 3 surfaces during the trial window, per the existing Live Issues SOP (Sev3s are fine — triaged normally, don't block). A single Sev1/Sev2 during the window blocks release until resolved and re-verified.
- **Sign-off (final say):** even with a clean bug bar, the trial isn't over until the user explicitly confirms it — daily real usage across all 4 projects and surfaces, not just a passive waiting period.
- **Window is a floor, not a ceiling:** the 1–2 week window may extend beyond 2 weeks even with zero Sev1/Sev2 issues, at the user's discretion — e.g. to validate more feature surface area, or to cover journeys/scenarios not represented in Phase 2's 7 journey groups that turn up during real use. There is no fixed trial-end date; it ends when both exit-criteria conditions are met, whenever that is.

**On successful exit:** proceed directly to the Named Release Policy steps already defined in the global CLAUDE.md (paused pending this initiative) — CHANGELOG entry, VERSION bump, `gh release create`, roadmap row → ✅ Shipped, blog post, one-sentence release pitch. This spec does not re-derive those steps; it only defines what must be true before they're invoked.

## GOVERNS Lifecycle Mapping

This effort maps onto synlynk's own 7-stage GOVERNS taxonomy (`synlynk/taxonomy.py`) as follows:

| Stage | This spec's activity |
|---|---|
| **Goal** | `goal-9ef9a965` ("Synlynk release announcement") is the governing goal for this readiness phase; `goal-85656c82` ("Developer Experience v1.0 (launch)") is the governing goal for the underlying UX 1.0 surfaces this phase validates. |
| **Open** | This spec itself — brainstormed and written under `goal-9ef9a965`. |
| **Visualize** | Phase 2 (Journey Map Simulator) — the `docs/brainstorm/ux-journey-map/` artifact is, literally, this stage's deliverable. |
| **Execute** | Phases 1 and 3 — the surface checklist verification and the nudge implementations, dispatched per the capability-based routing table. |
| **Release** | Phase 4's exit — CHANGELOG, VERSION bump, `gh release create`, per the Named Release Policy. |
| **Notify** | Phase 3's nudges are themselves a Notify-stage mechanism (in-product), separate from the release announcement itself. |
| **Sustain** | The Phase 4 trial window — daily real usage, Sev1/Sev2 bug bar, sign-off — is the Sustain-stage check before Release fires. |

**The gap this surfaced, and how it was closed for this spec:** while answering "where does this fit in GOVERNS," a direct query of this project's `state.db` found the `goal_contributions` link table completely empty — no story, including any of the 12 tasks that shipped PR #731, had ever been linked to a GOVERNS goal. The mechanism to link them (`synlynk goal link`, `synlynk story create`) existed and worked; nothing had ever called it. Concretely, for this spec:

- All 15 stories from the shipped UX 1.0 work (`story-issue-731`, `ux1.0-task1`–`ux1.0-task12`, `ux1.0-regression-fix`, `story-issue-746`) were retroactively linked to `goal-85656c82`.
- A new story (`story-6c5ff44e`, "UX 1.0 Field Trial Readiness — design spec") was created for this spec and linked primary to `goal-9ef9a965`, secondary to `goal-85656c82`.

**Standing discipline going forward (not a new mechanism, a correction to existing practice):** every dispatched task under this spec creates and links its own story as part of its own steps — via `synlynk story create` + `synlynk goal link` — rather than relying on a post-hoc PM sweep to reconstruct the linkage later. This is a process note for whoever dispatches Phase 1/2/3 work, not a code change.

**What this does not fix:** the systemic gap — no automated suggestion at spec/plan-approval moments, no way to mark a story `done`, no enforcement that new work gets linked — is real and tracked separately as `goal-90e73dfd`. That goal is priority work in its own right and is intentionally out of scope for this spec; this section documents the workaround applied here, not a resolution of the underlying mechanism.

## Out of Scope

- Automated smoke-test suite for the 3 surfaces (Phase 1 explicitly defers this to a follow-up ticket, post-trial).
- Any redesign of the surfaces themselves — this phase validates and visualizes what PR #731 already shipped; it does not change surface behavior except where Phase 1 uncovers real defects.
- Multi-tenant or team-mode nudge configuration — the `nudges` config block is user-level/local only, matching how budget config already works; team-mode nudge sync is not addressed here.
