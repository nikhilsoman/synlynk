# v0.26.0 — Daemon reliability Design Specification

## 1. Intent & Context

Following the release of `v0.25.6` (commit `67e9dcc1`, PR #2618), milestone `v0.26.0` focuses on **Daemon Reliability**. As specified in the canonical execution schedule (`2026-10-20-canonical-release-execution-schedule.md`, line 42), the daily stable gate for `v0.26.0` requires that:
> "Daemon reliability: restart, cancellation, recovery, scan containment, replay, and stop idempotence are evidence-tested. Revalidate #2464 and #1884; #2477 is closed and must not be reopened without new reproduction. Parent #2458; release epic #2468; goal goal-079e2f37."

Synlynk coordinates multi-agent workflows using a fleet of background daemons and child processes. Over recent releases, intermittent failures have surfaced around daemon stop idempotence, macOS fork-safety during GitHub App token minting, scratch workspace destruction during concurrent selftests, missing real-launch coverage for long-running CLI commands, and telemetry bloating in `sentinel.md`.

This design specification formalizes the architecture, failure recovery, process contracts, and verification plans for `v0.26.0`.

## 2. Taxonomy of the Synlynk Daemon Fleet

Synlynk's architecture relies on four distinct daemon tiers:

```
┌────────────────────────────────────────────────────────────────────────────────────────┐
│                                   SYNLNYK DAEMON FLEET                                 │
├─────────────────────────┬──────────────────────────┬───────────────────────────────────┤
│ 1. MAIN PLATFORM DAEMON │ 2. VIZOR WEB HUB DAEMON  │ 3. PERSONAL HOSTED RELAY DAEMON   │
│ (synlynk watch)         │ (synlynk viz daemon)     │ (synlynk relay)                   │
├─────────────────────────┼──────────────────────────┼───────────────────────────────────┤
│ • Role Token Refresher  │ • Local HTTP/FastAPI     │ • Embedded NATS JetStream server  │
│   (50-min JWT rotation) │ • Port Hunting Ladder    │ • Scoped device credentials       │
│ • Autonomy Pass Engine  │   (33333..11111)         │ • Durable JetStream replay        │
│ • AST Scan Containment  │ • SSE Event Streaming    │ • Reconnection & recovery         │
│ • Sentinel Health Pulse │ • PID: ~/.synlynk/vizor/ │ • PID: ~/.synlynk/relay/          │
│ • PID: ~/.synlynk/watch │                          │                                   │
└─────────────────────────┴──────────────────────────┴───────────────────────────────────┘
```

1. **The Main Platform Daemon (`SynlynkDaemon` & `WatchDaemon` in `synlynk/daemon.py` / `synlynk/watch.py`):**
   - Manages role token refresh (minting GitHub App JWTs every 50 minutes).
   - Executes background autonomy passes (`_autonomy_pass`) and task lease claiming.
   - Enforces AST scan containment (strictly skipping `.worktrees/`, `.claude/worktrees/`, and sub-worktrees per Sev1 LIVE-29 / #2477).
   - Coordinates process lifetime locking via `_lock_daemon_lifetime` and PID files.
2. **The Vizor Web Hub Daemon (`synlynk/vizor_daemon.py` & `synlynk/viz/`):**
   - Serves the local web interface and SSE event stream across the memorable port hunting ladder (`[33333, 44444, 55555, 22222, 11111]`).
   - Must cleanly release sockets and unlink pidfiles on SIGTERM without `TIME_WAIT` lockups.
3. **The Personal Hosted Relay Hub Daemon (`synlynk/relay_hub.py` & `synlynk/relay.py`):**
   - Embedded NATS JetStream publish/subscribe broker for cross-device synchronization.
   - Manages durable stream replay, reconnection backoffs, and message retention.
4. **Background Dispatch Job Workers (`daemon_jobs` table, `synlynk/jobs.py`):**
   - Asynchronous child processes spawned per dispatched task (`codex`, `grok`, `claude`, `agy`).
   - Monitored by `_reconcile_daemon_jobs()`, ensuring truthful exit code reporting and terminal cost/token attribution.

## 3. Workstream 1: Daemon Stop Idempotence & State Truth (gh:#2464)

### Problem
During QA review of PR #2462, `tests/test_synlynk.py::test_synlynk_daemon_stop_idempotent` was found to fail intermittently. When stopping an unstarted or already-stopped daemon, the command expected to print `not running`, but in certain environments reported `daemon stopped`.

Investigation revealed that `_resolve_live_pid()` in `synlynk/daemon.py` falls back to `_find_pid_listening_on_port(self.HTTP_PORT)` via `lsof -ti :<port>`. If any unrelated process or lingering socket was present on the port, `_resolve_live_pid()` mistakenly returned that PID. Furthermore, `SynlynkDaemon.stop()` and `WatchDaemon.stop()` had subtle discrepancies in state reporting, lock file unlinking, and return code handling.

### Architectural Solution
1. **Strict Mutual Exclusion on Stop:**
   - Both `SynlynkDaemon.stop()` and `WatchDaemon.stop()` must acquire the daemon lifetime lock (`_try_acquire_daemon_lock`) before modifying or inspecting state files.
   - If the lock is held by a live process, send `SIGTERM`, wait up to 1.0s (10 x 100ms polls), escalate to `SIGKILL` if still alive, and release/unlink the lock and pidfile.
2. **Identity-Corroborated PID Resolution:**
   - A PID reported by `lsof` or PID file must be validated via process start-time or cmdline corroboration before being treated as a live daemon target.
   - If `pid` is not alive (`kill(pid, 0)` raises `ProcessLookupError`), the pidfile and lockfile are treated as stale and cleaned up.
3. **Strictly Idempotent Output Contract:**
   - **Invocation 1 (Daemon was running):** Terminates process, cleans state, outputs `  ✓ synlynk daemon stopped.` (or `synlynk watch stopped.`).
   - **Invocation 2 (Daemon already stopped / absent):** Cleans any dangling artifacts, outputs `  ✦ daemon not running` (or `synlynk watch is not running.`), and exits 0.
   - Calling `stop()` $N$ times consecutively must never crash, never hang, and deterministically output `not running` on invocations $2 \dots N$.

## 4. Workstream 2: macOS Objective-C Fork-Safety & Canonical Absolute PEM Lookup (gh:#1884)

### Problem
Daemon logs on macOS intermittently surfaced fatal aborts:
```
objc[<pid>]: +[NSNumber initialize] may have been in progress in another thread when fork() was called. Crashing instead.
```
Followed immediately by cascading errors during GitHub App token minting:
```
openssl JWT signing failed for app_id=... .synlynk/github_apps/<role>.pem: No such file or directory
```

### Root Cause Analysis
1. **CWD Drift on Role PEM Lookups:** `_resolve_private_key_path()` and `_default_apps_dir()` in `synlynk/github_app_auth.py` fell back to CWD-relative `.synlynk/github_apps/` paths. When the daemon switched working directories or dispatched work into isolated worktrees, `os.path.exists()` on the relative path failed, causing the fallback to fail with `No such file or directory`.
2. **macOS Multi-Threaded Fork Hazards:** When the daemon executes background threads (e.g. autonomy pass, sentinel pulse), calling `subprocess.run(["openssl", ...])` invokes `fork()` internally. Under macOS Foundation and Security frameworks, calling `fork()` without immediate `execve` while another thread initializes runtime classes triggers Apple's `+[NSNumber initialize]` crash.

### Architectural Solution
1. **Canonical Absolute Key Resolution:**
   - Refactor `_resolve_private_key_path()` in `synlynk/github_app_auth.py` to unconditionally query canonical absolute paths via `synlynk.product_store.resolve_github_apps_dir()` and `~/.synlynk/github_apps/`.
   - Never return an un-anchored relative path (`.synlynk/github_apps/<role>.pem`). If the file cannot be located, fail with an explicit diagnostic detailing the checked canonical absolute paths.
2. **Subprocess Fork-Safety Isolation:**
   - In `synlynk/github_app_auth.py` and `synlynk/daemon.py`, ensure all subprocess invocations specify `close_fds=True` and pass environment variable `OBJC_DISABLE_INITIALIZE_FORK_SAFETY=YES` to child environments.
   - Provide fallback to pure-Python RSA/JWT signing if available, isolating token refresh from external shell invocations.

## 5. Workstream 3: Repair Scratch Cleanup Active Selftest Isolation (gh:#2407)

### Problem
Running `synlynk repair --confirm` calls `cleanup_selftest_workspaces()` in `synlynk/doctor.py`. Historically, this function deleted all `/tmp/synlynk-selftest-*` directories where mtime exceeded an arbitrary threshold, or if `.owner.json` was missing. When concurrent test suites or CI runners were executing selftests in `/tmp/synlynk-selftest-<hash>`, a background repair sweep unlinked the active working directory, causing concurrent git commands to crash with:
```
fatal: Unable to read current working directory: No such file or directory
```

### Architectural Solution
1. **PID Liveness + Lease Verification:**
   - Every selftest scratch directory created in `synlynk/selftest.py` writes `.owner.json` containing `{"pid": <pid>, "created_at": <epoch>}`.
   - `cleanup_selftest_workspaces()` must verify that:
     1. The owner PID is dead (`os.kill(pid, 0)` raises `ProcessLookupError`).
     2. AND the directory age exceeds `stale_before = time.time() - 3600`.
2. **Grace Period for Initializing Scratches:**
   - If `.owner.json` is missing or temporarily locked during creation, enforce a strict grace period: directories with mtime < 600s (10 minutes) must **never** be deleted.
   - Active selftest directories must be completely isolated from concurrent repair operations.

## 6. Workstream 4: Live Command Selftest Real-Launch Coverage (gh:#422)

### Problem
`synlynk/selftest.py` contains dedicated scenario runners for CLI commands (`init`, `scan`, `join`, `goal`, `story`, `decide`, `jobs`, `status`, `migrate`, etc.). However, long-running daemon commands—specifically `watch` and `viz`—fell through to `_generic_help_scenario()`, which only verified `--help` flag exit codes.

A catastrophic runtime failure (such as an immediate port binding collision, missing dependency import, or unhandled SIGTERM) in `synlynk watch` or `synlynk viz daemon` was invisible to `synlynk selftest`.

### Architectural Solution
1. **Dedicated Real-Launch Scenarios in `synlynk/selftest.py`:**
   - Implement `_scenario_watch(entry, ctx)`:
     - Spawns `synlynk watch --live` (or daemon start) in a sandboxed scratch environment with ephemeral PID path.
     - Captures stdout/stderr, verifying initialization banner within a 2.5-second bounded window.
     - Emits `SIGTERM` and asserts graceful exit code 0 and pidfile unlinking.
   - Implement `_scenario_viz(entry, ctx)`:
     - Spawns `synlynk viz daemon start` bound to an ephemeral unallocated port.
     - Verifies health HTTP response via localhost probe.
     - Terminates with `synlynk viz daemon stop` and verifies socket unbinding.
2. **Registration in `SELFTEST_SCENARIOS`:**
   - Register both commands in `SELFTEST_SCENARIOS` so `synlynk selftest --live` exercises genuine lifecycle execution.

## 7. Workstream 5: Sentinel Alert Aging, Deduplication Rollup, and Maintainer RSI Loop (`story-a4442387`, `story-2e48a8c5`)

### Problem
`.synlynk/sentinel.md` has accumulated over 559 lines (158KB) of unstructured and duplicate alert entries. Because past crashes interrupted alert writes, malformed strings (e.g. raw argparse usage snippets) were appended. Furthermore, because sentinel alerts have no active TTL pruning or automated triage, alerts persist indefinitely, cluttering the status dashboard and bloating context windows.

### Architectural Solution
1. **Compaction & Aging Engine in `synlynk/sentinel.py`:**
   - Implement `compact_sentinel_alerts(path: Optional[str] = None)`:
     - Parses all alerts using `_parse_sentinel_alert()`.
     - Discards corrupted lines that do not adhere to `[SEVERITY] [TIMESTAMP] CODE: MESSAGE`.
     - Purges alerts whose `last_seen_dt` is older than `active_ttl_seconds` (30 days for INFO/WARN, 7 days for auto-probe notices).
     - Deduplicates active alerts within the 24-hour window, rolling up occurrence counters (`[occurrences: N; first seen: ...; last seen: ...]`).
     - Rewrites the file atomically via temporary file and replace.
2. **Upstream Link to Maintainer Role Charter (v0.26.1 / gh:#2469):**
   - In accordance with the decision to establish an autonomous maintenance loop, `story-2e48a8c5` (*"Implement sentinel-to-shipped Platform Health & Performance maintenance loop"*) is chartered for `v0.26.1`.
   - `v0.26.0` provides the clean, aged telemetry substrate; `v0.26.1` equips the Maintainer agent with a wake-cycle SOP that triages active sentinel alerts, creates GitHub issues/stories, and automatically clears resolved alerts.

## 8. Harness² & Recursive Self-Improvement (RSI) Architectural Alignment

The open-sourcing of Google Research's **Harness²** ([arXiv:2610.14224](https://arxiv.org/abs/2610.14224)) provides a valuable theoretical validation of Synlynk's direction under epic **gh:#2547** (*"Harness velocity: measure session time and add evidence-driven RSI loops"*):

1. **Substrate Reliability as the Foundation of RSI:**
   Harness² formalizes that frozen base models achieve self-improvement through recursive mutations of the 8 file-mounted harness components (prompts, guardrails, memory, skills, tool guidance, scripts, subagents, plugins). In an autonomous RSI environment, the daemon is the perpetual runtime engine. If the daemon leaks PIDs, crashes on fork, or purges active workspace leases, the Propose–Probe–Compose loop collapses. The hardening in `v0.26.0` ensures the substrate is provably stable.
2. **Contrastive Probing and Telemetry Signal:**
   Harness² uses behavioral contrast (diffs, execution traces, failure logs) to grade harness mutations without ground-truth labels. The sentinel alert aging and deduplication implemented in Workstream 5 directly ensures that Synlynk's telemetry provides high-signal feedback for future Propose–Probe–Compose iterations.
3. **Forward Contract for v0.26.1:**
   In `v0.26.1`, Synlynk's agent charters will adopt the 8-component schema, allowing the Maintainer agent to autonomously propose fixes to harness scripts and SOPs when recurring sentinel faults are detected.
