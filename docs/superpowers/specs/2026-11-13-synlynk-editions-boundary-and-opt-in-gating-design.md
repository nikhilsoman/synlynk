# Synlynk Editions: Core / Opt-in / Hosted Boundary & Gating Mechanics

**Date:** 2026-11-13
**Status:** Approved
**Roadmap entry:** Previously referred to as "Spec #2" in `docs/superpowers/specs/2026-11-13-intent-based-engineering-and-roadmap-drift-governance-design.md`'s Deferred section ("Team/Enterprise full boundary and opt-in gating mechanics"). Per-edition onboarding journeys ("Spec #3") depend on this spec landing first.

---

## Context

The drift-governance spec (above) established the classification *rule* for Synlynk capabilities — every capability is classified by **who bears its marginal cost of existing**: Core (nobody extra), Opt-in (the user, via their own config/credentials — free), or synlynk-hosted/brokered (priced, because synlynk bears the cost) — and worked three examples (Vizor split, TPM daemon-tick, GOVERNS split) to prove the rule, explicitly deferring both the full module inventory and the actual code-level gating mechanics. This spec builds the mechanics and firms up the Team/Enterprise boundary beyond stub.

**Naming note:** `synlynk/addon.py` already exists and owns the term "add-on" for a shipped, unrelated concept — pre-vetted dev-tool bundles (Ruff/ESLint/Prettier, Gitleaks/Semgrep, Graphify/Mermaid). The drift-governance spec's third category, "Add-on" (synlynk-hosted/brokered, priced), is renamed **Hosted** throughout this spec and its implementation to avoid colliding with that existing module.

**Key finding from working the boundary concretely against today's code (not just the stub text):** Team edition is not a feature wall. Local relay (`synlynk/relay_hub.py`, `synlynk/relay.py`) already exists and is self-described in its own docstring as "Opt-in" — free, user-run, available today to any Personal-edition user who turns it on. Hosted relay doesn't exist yet, and per the drift-governance spec's own rule, synlynk-hosted/brokered items are **not edition-gated at all** — any tier can buy one à la carte. So nothing Team "adds" is actually blocked from a Personal user today; Team edition's real content is multi-seat licensing, default-preset bundling, and price bundling — not a capability gate. Enterprise's bolt-ons (SSO, RBAC, audit retention, data residency) are all deeper Platform-Vision-Phase-1-dependent than Team's items, and are named concretely below rather than left as a vague stub.

## Design

### 1. Classification Engine — `synlynk/editions.py`

A registry-based classification, not a decorator scattered across call sites, so the full inventory can be generated by iterating one structure rather than grepping the codebase:

```python
EDITION_ORDER = ("personal", "team", "enterprise")  # ordinal rank

@dataclass(frozen=True)
class Capability:
    name: str                      # e.g. "agent_studio", "hosted_relay"
    category: str                  # "core" | "opt_in" | "hosted"
    min_edition: str | None = None # ordinal gate; None for core/opt_in
    hosted_key: str | None = None  # e.g. "hosted_relay"; required iff category == "hosted"
    note: str = ""                 # one-line "why", surfaced in the generated inventory

CAPABILITIES: dict[str, Capability] = { ... }  # populated by the inventory task (Section 5)
```

Two independent check primitives, matching the two things that can actually gate behavior — a plain function call at the call site, not a decorator, so the gate is visible exactly where the gated behavior starts:

```python
def check_edition(config: dict, capability_name: str) -> tuple[bool, str]:
    """Ordinal check: does config['edition'] rank >= the capability's min_edition?
    core/opt_in capabilities always return (True, "") -- edition never blocks
    them, it only affects which higher-tier defaults are pre-enabled elsewhere."""

def check_hosted(config: dict, capability_name: str) -> tuple[bool, str]:
    """Membership check: is capability's hosted_key in config['hosted']?
    Only meaningful for category == "hosted"; raises on misuse (calling it
    against a core/opt_in capability is a programming error, not a runtime gate)."""
```

An unknown capability name raises `KeyError` in both helpers — a typo'd name must never fail open.

### 2. Config Surface

`.synlynk/config.json` gains two additive keys, both defaulting to safe no-op values so every existing installation keeps working with zero migration:

```json
{
  "edition": "personal",
  "hosted": []
}
```

- **`edition`** — one of `EDITION_ORDER`, defaults to `"personal"` when absent.
- **`hosted`** — flat list of hosted-capability keys (e.g. `["hosted_relay"]`), defaults to `[]`. Independent of `edition` — a `"personal"`-edition install can carry hosted entries; a `"team"`-edition install isn't implicitly granted any (per Section 3's finding that hosted items aren't edition-gated).

**No seat-counting, no license file, no signature.** This is a soft, advisory config value the operator sets by hand (or via the `synlynk edition` CLI in Section 4). There is deliberately no tamper-resistance here — correct until Platform Vision Phase 1's real Account/Plan model exists, and this spec states that tradeoff explicitly rather than implying false rigor.

`check_edition`/`check_hosted` take a plain `dict`, reusing however config already gets loaded for `require_linked_goal_mode` and friends in `policy_gates.py`/`db.py` — no new config-loading path.

**Validation (advisory only):** a new `synlynk doctor` check, `_hc_editions_config()`, warns (never blocks) if `edition` is unrecognized or `hosted` contains an unknown key — same `HealthCheck` pattern as the roadmap-drift check from the prior epic.

### 3. Team/Enterprise Boundary, Firmed Up

**What Team edition concretely gates — none of it a feature wall:**
1. **Multi-seat licensing** — the commercial unit (N human operators, one account/invoice). Unenforceable in code today (no Account system — Phase 1); recorded here as the *intended* meaning of the `edition` value, honor-system until Phase 1 lands.
2. **Default-preset bundle** — a `DEFAULT_HOSTED_BY_EDITION` map consulted by `synlynk edition set`/`synlynk init` (not a runtime gate) that pre-populates `hosted: ["hosted_relay"]` for Team, versus `[]` for Personal.
3. **Price bundling** — hosted relay's cost is included in Team's price instead of charged separately. Pure billing; not represented in code at all, correctly, since that's Phase 1's job.

**Enterprise's bolt-ons, named concretely instead of left as a stub:**

| Bolt-on | Category | Phase-1 dependent? |
|---|---|---|
| Audit log retention/export | Hosted | Yes — needs durable per-Account storage |
| SSO (SAML/OIDC) | Hosted | Yes — needs the Account/Org model to attach identities to |
| RBAC (role-scoped permissions) | Core-complexity, Enterprise-only availability | Yes — meaningless without multi-user Accounts |
| Compliance data-residency controls | Hosted | Yes — needs multi-region infra |

All four are more deeply Phase-1-dependent than Team's items; none can be partially stood up locally the way Team's config-flag defaults can. Each is a `category: "hosted"` / `min_edition: "enterprise"` registry entry with `note: "blocked on Platform Vision Phase 1"` — visible in the generated inventory as a named dependency rather than silence.

**Unchanged from the drift-governance spec and reaffirmed here:** remote relay, hosted workstation, and swarm gateway are not edition-gated — any tier can buy one individually, since they're Hosted by the cost-bearer test, not features reserved for a tier.

### 4. `synlynk edition` CLI

A small convenience command, since the registry is otherwise inert without an easy way to set it:

- `synlynk edition show` — prints the current `edition` and `hosted` list from config.
- `synlynk edition set <tier>` — validates `<tier>` against `EDITION_ORDER`, writes it to config, and applies `DEFAULT_HOSTED_BY_EDITION`'s preset for that tier to the `hosted` list (additive — never removes a hosted key the operator already had).

### 5. Worked Examples (this spec) vs. Full Inventory (the implementation plan)

Beyond the drift-governance spec's three examples (Vizor split, TPM daemon-tick, GOVERNS split), these prove the test generalizes across different functional areas of the codebase:

| Capability | Category | Why |
|---|---|---|
| `capability_*.py` family (12 modules — tracking, probing, backfill) | **Core** | Local self-measurement of the user's own dispatch history; nobody but the local runtime bears this cost. |
| `local_pilot*.py` (single-operator orchestration) | **Core** | The Wingman default itself — this *is* what Personal runs on, not an extra. |
| `gh_role.py` / `github_app_auth.py` | **Opt-in** | The user's own GitHub App, their own credentials — named explicitly in the drift-governance spec's own Opt-in examples. |
| `relay.py` / `relay_hub.py` | **Opt-in** | Local relay, peer-to-peer, user bears the cost — already self-described as "Opt-in" in the module's own docstring. |
| `quota.py` / `quota_capture.py` | **Core** today | Tracks usage against the user's own API keys. Splits to **Hosted** the moment synlynk operates its own bulk-purchased model router (consumption/task-based billing) — not built, so the split is latent, not active. |
| `swarm.py` | **Core** (local dispatch across worktrees) / **Hosted** (the not-yet-built Swarm Infrastructure Provisioning Gateway, Platform Vision Phase 4) | Same shape as the Vizor split — today's code is Core; the cloud-provisioning extension Phase 4 describes is Hosted because synlynk would bear the infra cost. |

**The full 212-module pass** (not ~138 — recounted directly via `ls synlynk/*.py`, correcting the drift-governance spec's stale estimate) is an implementation-plan task: walk every module, classify against the test above, flag genuine ambiguities, and emit `docs/strategy/editions-inventory.md` (human-readable) + `docs/strategy/editions-inventory.json` (structured — seeds `CAPABILITIES` in `editions.py` directly, so classification work and the registry aren't duplicated effort).

## Deferred (explicitly out of scope for this spec)

- **Per-edition onboarding journeys** ("Spec #3") — depends on this spec landing first, per the original sequencing.
- **Real billing/seat enforcement, SSO, RBAC, audit retention** — all blocked on Platform Vision Phase 1 (Accounts/Entitlements); named concretely in Section 3's table but not built.
- **A `doctor` check diffing the registry against live `check_edition`/`check_hosted` call sites** — deferred until a real call site exists to drift against; building drift-detection for zero call sites is premature.
- **"Outsource to synlynk" outcome-based delivery** — already flagged deferred in the drift-governance spec, still deferred here.
- **Retrofitting GOVERNS/Agent Studio's existing toggles** (`require_linked_goal_mode`, etc.) to derive from the edition value — this spec's edition/hosted axis sits alongside those toggles untouched; they keep working exactly as they do today.

## Testing / Rollout

- `tests/test_editions.py` — `check_edition()` ordinal comparison (including equal-rank and unknown-capability `KeyError`), `check_hosted()` membership (and that calling it against a non-`hosted` capability is a programming error, not a silent pass), and a registry-shape invariant (`category == "hosted"` implies `hosted_key` is set; `core`/`opt_in` implies `min_edition is None`).
- `tests/test_doctor_editions_config.py` — `_hc_editions_config()` warns on an unrecognized `edition` string or unknown `hosted` key, passes silently on absent keys and on valid values.
- `tests/test_editions_inventory_schema.py` — the generated `editions-inventory.json` validates against the same shape `CAPABILITIES` expects, so the inventory-generation task and the registry can't silently drift apart from day one.
- **Rollout is intentionally low-risk and purely additive:** two new config keys (both default to safe no-op values) and one advisory `doctor` check. Nothing gates any existing command's behavior yet — `check_hosted()`'s first real caller will be whichever future spec actually builds hosted relay/SSO/etc. No `observe`/`enforce` phase-in is needed here, unlike the roadmap drift gate, because there is no blocking behavior to phase in.
