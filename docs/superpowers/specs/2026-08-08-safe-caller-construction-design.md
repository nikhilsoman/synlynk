# Safe Caller Construction — Design

## Context

Issue #720 ("Fail closed on empty dispatch tasks and enforce task/scope integrity") specified
6 required behaviors, tracked via #769 after two sub-projects shipped: the fail-closed
empty-task guard + inspectability (PR #759), the task-receipt protocol (PR #768), the
permission-denied classifier fix (PR #770/#771), and scope enforcement (PR #778). This design
covers the sixth and final requirement: documenting safe caller construction so that automated
callers of `synlynk dispatch` build task text as structured data rather than an interpolated
shell string.

## Problem

`synlynk dispatch <agent> --task "<text>"` is a shell command. Any caller that builds the
`--task` value by string-formatting untrusted or dynamic content into a shell command line is
exposed to the same class of bug as SQL string concatenation — a task string containing shell
metacharacters can break out of the intended argument boundary. Nothing in the codebase
currently documents a safe alternative, even though one already exists: `dispatch_agent()` in
`synlynk/dispatch.py` takes `task` as a plain Python `str` parameter and never touches a shell.
Issue #720 asks for this to be published as guidance, not new enforcement code.

## Non-goals

- No new CLI flag or wire format in this sub-project. A structured `--task-file`/stdin JSON
  interface for non-Python CLI callers is a real future need — expected to become necessary
  once Team/Enterprise (targeted September 2026) introduces external, non-Python, non-human
  callers (webhooks, API gateway, other services) invoking dispatch programmatically — but no
  such caller exists today. Building it now would be speculative. This design produces a
  tracked, named follow-up issue instead (see "Deferred: `--task-file` interface" below), so
  the gap isn't rediscovered from scratch when Team/Enterprise work starts.
- No change to `dispatch_agent()`'s signature or behavior — it already does the right thing.

## Design

### New file: `docs/reference/safe-caller-construction.md`

Hand-written, not generated. Three sections:

**1. Python callers (recommended path).** Show `dispatch_agent()` called directly:

```python
from synlynk.dispatch import dispatch_agent

result = dispatch_agent(
    agent="codex",
    task=task_text,          # plain str — no shell involved
    story_id=None,
    context_mode="full",
)
```

State plainly: this is already structured data. `task_text` can come from anywhere (a template,
user input, another API response) without any escaping step, because it never passes through a
shell. This is the pattern synlynk's own internal callers already use — point to
`synlynk/capability_sweep.py`'s `dispatch_agent(agent, task, **dispatch_kwargs)` call site
(`capability_sweep.py:127`) as a live example via a `grep`-able reference, not a duplicated
snippet that can drift.

**2. Shell/CLI/automation callers (do/don't pair).** For callers who must shell out (CI steps,
non-Python scripts):

- **Don't:** build a shell command string by interpolating task text, e.g.
  `os.system(f'synlynk dispatch codex --task "{task_text}"')` — breaks the moment `task_text`
  contains a `"`, `` ` ``, `$(...)`, or a newline.
- **Do:** invoke as an argument list with `shell=False` (the default for `subprocess.run` when
  passed a list), so the OS never re-parses the string:
  `subprocess.run(["synlynk", "dispatch", "codex", "--task", task_text])`.
- **One-line note for bash callers who must build a literal shell string** (e.g. inside a
  Makefile or a `.sh` script, where a Python list isn't available): use `shlex.quote()` (or the
  shell's own `printf %q` equivalent) to quote the value — never hand-roll escaping.

**3. `--dry-run` recommendation.** Point to the existing `--dry-run` flag (PR #759) and
`jobs --summary`'s `task_sha256`/`task_preview` fields as the way to verify what a dynamically
constructed task string actually resolved to, before it dispatches for real. Recommend any
automation call site run a `--dry-run` pass in CI or on first integration, not on every
invocation.

**4. Known gap.** One paragraph: a structured `--task-file <path>.json` / stdin interface for
non-Python CLI callers doesn't exist yet. Link the new issue (see below). Explicitly frame it as
deferred to the Team/Enterprise cycle, not a current limitation callers need to work around
today (today's callers are internal/Python, where `dispatch_agent()` already suffices).

### Discoverability: link from `docs/reference/commands.md`

`docs/reference/commands.md` is fully auto-generated by
`scripts/generate_command_docs.py::render_reference_doc()` (`Path(...).write_text(...)` — a full
overwrite, no preserved-section markers, header states "Do not edit by hand"). Hand-adding a
link directly to the generated file would be silently wiped on the next regeneration. Instead,
add the link inside the generator itself:

**Modify:** `scripts/generate_command_docs.py`, `render_reference_doc()` — after the existing
"Generated from `synlynk/taxonomy.py`. Do not edit by hand..." line, add one line:

```python
lines.append("See [safe-caller-construction.md](safe-caller-construction.md) for guidance on "
             "building dispatch task text programmatically.")
```

This is an edit to the generator's source, not to generated output — it survives every future
regeneration. Regenerate `docs/reference/commands.md` as part of this sub-project's own commit
(`python3 scripts/generate_command_docs.py`) so the link is live immediately.

### Deferred: `--task-file` interface (new issue)

File a new GitHub issue: **"Structured task-file/stdin interface for `synlynk dispatch`
(Team/Enterprise prerequisite)"**. Body: references this design doc and #720/#769's original
requirement 6 framing; states the trigger condition (non-Python/non-CLI callers appearing,
expected with Team/Enterprise work starting ~September 2026); explicitly not scheduled, not
scoped to a specific implementation yet — a placeholder for when it becomes real. Not part of
this sub-project's task list; filed as a standalone step, same as #781 was for the SCOPE_VIOLATION
sub-project.

## Testing

Docs-only change plus one generator-source edit. No new runtime behavior to unit-test.
Verification is: `python3 scripts/generate_command_docs.py` regenerates `commands.md` with the
new link line and no other diff; `tests/test_docs_sync.py` (which checks generated content, not
this new file) continues to pass unchanged; a manual read-through confirms the Python example in
`safe-caller-construction.md` is copy-paste-runnable against the current `dispatch_agent()`
signature (verified against `synlynk/dispatch.py:1635-1651` as of this design).

## Out of scope

- Building the `--task-file` interface itself (tracked separately, see above).
- Any change to `dispatch_agent()`, `cli.py`'s `dispatch` subcommand, or scope/receipt/classifier
  enforcement — all three already shipped in prior #769 sub-projects.
- README.md changes — the existing `<!-- commands:start -->/<!-- commands:end -->` block only
  covers Tier-0 orientation commands, not reference docs; `safe-caller-construction.md` isn't
  Tier-0 material and doesn't belong there.
