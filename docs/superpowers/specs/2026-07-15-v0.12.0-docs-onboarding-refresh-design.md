# v0.12.0 Docs/Onboarding Refresh — Design

## Context

synlynk just shipped v0.12.0 (PR #268, tag `v0.12.0`, `gh release` live), rolling up 71 PRs since v0.11.0 (2026-07-05). The CLI's command surface has grown to 40+ top-level commands. User-facing documentation has not kept pace:

| Surface | Last real update | Gap |
|---|---|---|
| `README.md` | v0.10.0 (2026-07-01) | Missing all v0.11.0 + v0.12.0 commands |
| `docs/synlynk-quickstart-guide.html/.pdf` | v0.9.4 (2026-06-24) | Same |
| `docs/synlynk-command-reference.html/.pdf` | v0.9.4 (2026-06-24) | Same |
| `docs/synlynk-official-reference.html/.pdf` | v0.9.4 (2026-06-24) | Same |
| `website/src/docs.njk` (synlynk.com docs page) | 2026-06-28 | Command blurb lists only 7 commands |
| `docs/blog/*.md` | current through post 64 | Current, but all engineering-diary style — no reader-facing "what's new" post |

**Correction found during planning:** `website/src/changelog.md` is not a hand-maintained file — `website/.eleventy.js` (lines 67-88) auto-generates it from the root `CHANGELOG.md` at every `npm run build`, converting version headers and section tags into styled HTML. Since `CHANGELOG.md` is already current (v0.12.0, from the just-cut release), the website changelog page is already correct as of the next build — no separate update task needed. The stale "v0.9.8" content the original audit found was a stale build artifact on disk, not a real doc-maintenance gap.

`SYNLYNK_GUIDE.md` (repo root) was also flagged as untouched since the initial commit, but investigation showed it is not a user-onboarding surface — it documents this project's own AI-agent session protocol (referenced by `CLAUDE.md`'s "Session Protocol" section) and is not scaffolded into other repos by `synlynk init`. It gets a light consistency check only (see Task scope below), not a full rewrite.

The 3 canonical doc bundles (Quick Start, Command Reference, Official Reference) are hand-authored, self-contained styled HTML files with an explicit in-file maintenance contract (from `docs/synlynk-quickstart-guide.html`):

```
MAINTENANCE: Update this document after each release.
Official Reference: update version tag, add features page, update changelog + commands + comparison matrix.
Command Reference: update commands section for any new/changed commands.
Quick Start Guide: update version tag only unless UX flow changed.
```

PDFs are exported by hand (browser print-to-PDF) after editing the HTML — there is no build script. This is a known, accepted process, not a gap to fill.

There are also leftover variant files with no ongoing purpose: `docs/synlynk-quickstart-apple.html/.pdf`, `docs/synlynk-quickstart-compact.pdf`, and root-level `synlynk_quick_start.pdf`. These are retired as part of this work (deleted, not updated) — maintaining 3 canonical docs per release is already real work; extra variants only add drift risk.

## Goal

Bring every user-facing doc surface current with the v0.12.0 command surface, reorganized around **user journey stage** rather than the previous flat/alphabetical structure, with a distinct **"Upgrading?"** callout for existing users, and one new reader-facing **"what's new"** blog post distinct from the existing engineering-diary PR posts.

## Content Spine

This is the single source of truth every deliverable below translates into its own format. Do not re-derive the command list independently per surface — that repetition is exactly how the 4 surfaces drifted out of sync with each other before.

### Upgrading? (embedded in every surface)

```
If you installed synlynk before 2026-07, here's what's new:

- `synlynk schedule` — fleet batch dispatch, dry-run by default
- `synlynk cost log` — manual cost entries for native/PM-session work
- `local` agent — 5th dispatch target, zero-cost on-device inference
- `synlynk status` now shows a RATES line (rate-table staleness)
- `synlynk viz` — web HUD (Architect Map, Effort & Cost tab, Business Goals Panel)

Run `synlynk upgrade` to get the latest, then `synlynk doctor` to verify.
```

Exact command descriptions above are pulled from `synlynk/cli.py`'s `add_parser(..., help="...")` calls where available; a few (`probe`, `launch`, `decide`, `scan`, `migrate`, `repair`, `sync`, `exit`, `shell`, `open`) had generic/multi-line help text not fully captured here — each implementing plan MUST re-read the actual `help=` string (and `--help` flag list) for its own command entries from `synlynk/cli.py` directly rather than relying solely on this table's shorthand, since this table is a categorization aid, not a verbatim copy source.

## Execution Model

All 4 plans are content-translation work with no code logic and no shared file overlap (README.md / docs/*.html+pdf / website/* / docs/blog/*.md are disjoint), so they dispatch and execute in parallel — no sequencing dependency between them. Each plan's final task is a self-verification step (not dispatched, or dispatched with an explicit verification instruction):
- Plan 1: grep every command name mentioned in the new README table against `synlynk/cli.py`'s actual `add_parser` calls — zero orphans.
- Plan 2: same grep audit for the 3 HTML docs; confirm PDF file sizes changed (proof of re-export, not a stale copy).
- Plan 3: `npm run build` succeeds; same grep audit for `docs.njk`.
- Plan 4: `ls docs/blog/` confirms no numbering collision; spot-check all command names against `cli.py`.

## Out of Scope

- Automating the PDF export pipeline (still manual print-to-PDF, matches existing process).
- Any change to `CHANGELOG.md` itself (already current from the v0.12.0 release).
- Deep restructuring of `SYNLYNK_GUIDE.md` beyond the light consistency check noted in Plan 1.
- Non-English localization.
