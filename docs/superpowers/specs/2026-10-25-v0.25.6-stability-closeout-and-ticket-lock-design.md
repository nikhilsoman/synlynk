# v0.25.6 — Stability closeout and ticket lock Design Specification

## 1. Intent & Context

Following the successful delivery of release `v0.25.5` under Agy as Home Conductor, `v0.25.6` serves as the daily stability gate and ticket lock before moving towards the autonomous operating day milestone (`v0.26.3`) and Developer Preview (`v0.27.5`).

The release mandates three foundational governance pillars:
1. **Governed Roadmap Phase Update & Reassignment (gh:#2535):** Eliminate ad-hoc direct database manipulations by providing a policy-gated, transactional CLI command (`synlynk roadmap update` / `reassign`) to update and move phases across arcs.
2. **Backlog Disposition & 94 Ticketless Candidates Lock:** Provide an explicit, evidenced disposition (active mapped, post-preview deferred, or archived) for all 94 ticketless candidates cataloged in `docs/strategy/2026-10-20-canonical-release-execution-schedule.md`, ensuring all active stories link to an active goal, release epic, and live issue.
3. **Universal 4-Point Attribution Mandate:** Enforce that every story, issue, spec, plan, and decision panel decision is anchored to four coordinates: **Goal** (`GOVERNS`), **Epic** (Parent issue), **Release Milestone**, and **Arc**.
4. **Provenance & Job Purpose Resolution (gh:#2606):** Repair dispatch purpose defaulting and attestation overrides so cross-harness provenance verification in `synlynk pr check` operates truthfully without false-closed rejections.

## 2. Workstream 1: Governed Roadmap Phase Update & Reassignment (gh:#2535)

### Problem
Historically, `synlynk roadmap add` only permitted inserting new arcs or appending phases. When a phase required status changes, note updates, or relocation to a different release arc (such as deferring provider/OpenRouter phases to post-preview), developers or agents were forced to edit SQLite directly or leave stale records in `state.db`.

### Architecture & Specification

#### CLI Syntax
```bash
synlynk roadmap update \
    [--phase-id <id>] \
    [--arc <source_arc_version>] \
    [--phase-title <exact_title>] \
    [--target-arc <dest_arc_version>] \
    [--title <new_title>] \
    [--status <planned|in_progress|done|deferred|superseded>] \
    [--priority <P0|P1|P2|P3>] \
    [--story-id <story-id>] \
    [--notes <notes>] \
    [--role <role>]
```
Alias: `synlynk roadmap reassign` (identical options, emphasizing arc transfer).

#### Policy & Authority Enforcement
- Requires authority `roadmap_edit` validated via `synlynk.policy.check_authority("roadmap_edit", role=role)`.
- If unauthorized, fails closed with `RuntimeError: Roadmap edit refused: role <role> is not authorized per policy.json.`

#### Identification & Validation Rules
- Stable identifier lookup:
  - If `--phase-id` is provided, fetch `roadmap_phases` by `id`.
  - Else if `--arc` and `--phase-title` are provided, query `roadmap_phases WHERE arc_version=? AND phase_title=?`.
  - If neither or both are ambiguous/missing, raise `ValueError("Must specify --phase-id or both --arc and --phase-title")`.
- If no row matches, raise `ValueError("No roadmap phase found matching identifier")`.
- If multiple rows match `--arc` and `--phase-title`, fail closed and require `--phase-id`.
- If `--target-arc` is specified:
  - Verify `SELECT 1 FROM roadmap_arcs WHERE version=?`. If not found, raise `ValueError("Target arc version does not exist in roadmap_arcs")`.
  - Transactionally update `arc_version = target_arc`.
- Update allowed fields:
  - `phase_title = title` (if `--title` provided)
  - `status = status` (if `--status` provided, validating against allowed statuses)
  - `priority = priority` (if `--priority` provided)
  - `story_id = story_id` (if `--story-id` provided, verifying foreign key in `stories`)
  - `notes = notes` (if `--notes` provided)

#### Projection Verification & Rollback
- All mutations run inside a SQLite transaction.
- Upon commit, trigger `synlynk.db._generate_roadmap_md()`.
- If markdown generation fails or produces corrupted projections, the database transaction rolls back and an error is returned.

4. **Residual Stale Candidates:**
   - Mark `archived` or `superseded` with clear documented rationale.

## 4. Workstream 3: Universal 4-Point Attribution Mandate

### Attribution Invariant
Every unit of planned or active work must carry:
1. **Goal:** Active `goal_id` (e.g. `goal-9ef9a965`).
2. **Epic:** Active parent tracking issue (e.g. `#2458` or child epic `#2468`).
3. **Milestone:** Release target (e.g. `v0.25.6`, `v0.26.0`).
4. **Arc:** Subsystem track (e.g. `governance`, `runtime`, `dispatch`, `ci`).

### Verification Surface
- **Stories:** `synlynk story list` audited to ensure no active story lacks goal/epic/ticket coordinates.
- **Documents:** Audit frontmatter in `docs/superpowers/specs/` and `docs/superpowers/plans/` to require:
  ```yaml
  goal: "<goal_id>"
  epic: "<#epic_id>"
  milestone: "<milestone_tag>"
  arc: "<arc_name>"
  ```
- **Decide Panels:** `synlynk decide --panel` decisions recorded in `decisions` table must include goal and issue linkage.

## 5. Workstream 4: Provenance & Job Purpose Resolution (gh:#2606)

### Problem
In `synlynk/dispatch.py`:
```python
def _job_purpose(role: str | None, task_type: str | None, *, explicit: bool = True) -> str:
    if not explicit:
        return "other"
    ...
```
When `task_type` is unset, `_job_purpose` writes `daemon_jobs.purpose='other'`.
Then in `synlynk/db.py`:
```python
def _job_has_implementation_purpose(conn, job_id: str | None) -> bool:
    ...
    if row[0] == "implementation":
        return not attestation_exists
    if row[0] is not None:
        return False
    attestation = get_valid_job_provenance_attestation(conn, job_id)
    return bool(attestation and attestation["purpose"] == "implementation")
```
If `daemon_jobs.purpose` is `"other"`, `row[0] is not None` returns `False` immediately, bypassing `job_provenance_attestations` completely. This breaks post-hoc attestation repair for historical jobs.

### Fix
1. In `synlynk/dispatch.py`:
   - If `role == "dev"` and `task_type` is omitted, check task content or default to `"implementation"` rather than `"other"`.
2. In `synlynk/db.py`:
   - Check `get_valid_job_provenance_attestation(conn, job_id)` FIRST. If an explicit valid attestation exists, its purpose overrides `daemon_jobs.purpose`.
   - If no valid attestation exists, fallback to `row[0] == "implementation"`.
