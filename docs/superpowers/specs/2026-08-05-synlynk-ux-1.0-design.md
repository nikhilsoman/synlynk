# Synlynk UX 1.0 — TUI + Vizor Design

**Status:** Draft, pending user review
**Date:** 2026-08-05
**Author:** Claude (PM/brainstorm role), in dialogue with Nikhil

## Motivation

Fragmented daily-use pain: job/dispatch monitoring, fleet/cost state at a glance, too many subcommands to remember, and context-switching across terminal panes. Synlynk today is a CLI-only wrapper (`bin/synlynk.py`) plus a local web HUD (Vizor, `synlynk viz` @ localhost:8721, shipped v0.10.0). Neither is a complete daily-use surface on its own, and the existing roadmap's v0.9.0 "Review TUI" item is scoped narrower (phase-review only) than what's actually needed for daily fleet/job/cost operation.

## Scope for this 1.0 effort

**In scope:** Two independently-complete UX surfaces — a terminal TUI and the existing Vizor web HUD — both covering the full core operational loop (view fleet/job/cost status, dispatch, review, approve/merge, kill). "Independently complete" means **complete-for-medium**, not literal feature parity: both cover the core loop, but Vizor is expected to carry richer visual-only capability (gantt/tube views, cost graphs) that a terminal shouldn't try to replicate in ASCII/braille. Both surfaces are local-first and fully write-capable from day one — Vizor stays bound to `localhost` for 1.0, so write actions are exactly as safe as running the CLI yourself; no auth is needed yet because there is no second user.

**Also in scope:** a shared `uxcore` library that both surfaces call into, forward-looking extensibility seams for Team/Enterprise (actor/role, RBAC, feature flags, capability manifest, event log), a documented public interface for third-party ("BYOUX") consumers of that same library, and one real reference BYOUX consumer — a minimal one-way Slack notifier.

**Explicitly out of scope — named future phases, not built now:**
- IDE integration (as its own UX surface)
- Full two-way conversational bot surface (Slack/Teams/Discord slash-commands, interactive dispatch/approval from chat) — the Slack *notifier* in this spec is one-way only and does not imply this phase has started
- OAuth + Synlynk accounts for Vizor Team/Enterprise (Vizor stays localhost-only in 1.0)
- A remote/network `uxcore` API (HTTP shim) for BYOUX consumers running outside this process — 1.0's `uxcore` is a Python library contract, not a network service
- Real RBAC enforcement and a tiered feature-flag backing store — 1.0 ships the seams (typed `Actor`/`Role`, capability-manifest function, static flags file), not a policy engine

## Architecture

### `synlynk/uxcore.py` — shared core

The single source of truth for both surfaces and any future BYOUX consumer. Plain, synchronous Python functions, grouped:

- **Read:** `get_fleet_state()`, `get_jobs()`, `get_costs()`, `get_gantt_data()` — return typed dataclasses (not raw dicts), no HTTP/curses/Jinja mixed in. Replaces the logic currently inlined in `generate_viz_data()` (`synlynk/viz.py`); that function becomes a thin wrapper that calls `uxcore` and shapes the result for Vizor's templates/charts.
- **Write:** `dispatch(agent, task, actor=None, **flags)`, `approve_pr(pr_number, actor=None)`, `kill_job(job_id, actor=None)` — wrap the existing dispatch/`gh` subprocess plumbing so the TUI's keypress handler and Vizor's POST routes call the same function instead of each re-implementing it.
- **Capability manifest:** `list_capabilities(actor) -> list[Capability]` — computed from `actor.role` × active feature flags. Every consumer calls this once and renders/hides menu items and panels from the result, rather than hardcoding permission checks per surface.
- **Subscribe:** `subscribe(event_types=None) -> Iterator[Event]` — tails `.synlynk/events.jsonl` and yields structured, JSON-serializable events as they're appended. Used by the Slack notifier today; the same stream backs Team/Enterprise notifications later.

### Actor, Role, and the write chokepoint

- **`Actor`** — every `uxcore` read/write function takes `actor: Actor | None = None`, defaulting to a `LocalActor` singleton with `role = "owner"` (everything permitted; there is no other user in 1.0). This shapes the parameter now so Team/Enterprise identity can populate it later without changing call sites in `tui.py`/`viz.py`.
- **`Role`** — a typed enum (`owner`, `member`, `viewer`, ...) defined now; 1.0 only ever instantiates `owner`.
- **`_execute_write(action, actor, **params)`** — the single internal chokepoint all writes funnel through. It re-checks `list_capabilities(actor)` before running the underlying operation, then appends a structured event (`{actor, action, params, timestamp, result}`) to `.synlynk/events.jsonl`. This is where policy checks and notification hooks attach later — one interception point, not one per surface per write type.
- **`FeatureFlags.is_enabled(flag, tier)`** — orthogonal to RBAC (RBAC answers "can this actor do X," flags answer "does this deployment tier have X at all"). 1.0 reads a static `features: {}` block from `.synlynk/config.json` at startup; no remote flag service.

### `synlynk/tui.py` — terminal surface

Curses-based, stdlib only (matches the existing v0.9.0 roadmap commitment — no new dependency on the default path). A main event loop with numbered panels (Fleet, Jobs, Costs, Review) mirroring Vizor's navigation rather than inventing new information architecture. Each panel is a render function taking a `uxcore` read result plus a curses window; panels don't call `uxcore` beyond their own data need, so they're testable by rendering from a fixture dict with no live state or real terminal required (curses supports headless/pad-based rendering for this).

`--ui textual` remains the existing roadmap escape hatch for a richer Rooms/multi-pane layout — an alternate renderer over the same `uxcore` calls, not a fork of the data layer.

### Vizor (`synlynk/viz.py`) — web surface

Stays the existing local server; its routes become callers of `uxcore` instead of owning logic directly. New write routes (dispatch/approve/kill) call the same `uxcore` write functions the TUI uses — this is where Vizor's write capability actually lands. Remains localhost-only in 1.0.

### BYOUX — `uxcore` as a documented public interface

`uxcore` is a stable, documented Python library contract, not an internal implementation detail. Deliverable: `docs/api/uxcore.md`, written as a library README (assume the reader has never seen synlynk's internals) covering every public function's signature and return type, the capability-manifest pattern, and the actor/role model. A BYOUX consumer (e.g. a Herdr pane) imports `synlynk.uxcore` directly and calls the same functions the TUI and Vizor use — read, write, capability manifest, and `subscribe()` for live updates, all in-process.

Out of scope for 1.0: a process-boundary API for consumers not running in the same Python process/venv (see "Explicitly out of scope" above).

### Reference BYOUX consumer — minimal Slack notifier

`synlynk/notifiers/slack.py`, run via `synlynk notify slack --webhook-url <url>` as its own process. Calls `uxcore.subscribe(event_types=["dispatch_complete", "pr_approved", "job_failed"])` and posts a formatted message to a Slack Incoming Webhook URL per event. One-directional only: no bot token, no slash commands, no interactive buttons, no per-channel routing, no OAuth — a webhook URL is the only credential. Exists to force `subscribe()`'s event payloads to be genuinely externally-serializable before any other external consumer (Herdr, or the future full bot surface) depends on the contract.

## Data Flow

**Read:** surface (TUI panel / Vizor route / BYOUX consumer) → `uxcore.get_*()` → reads `.synlynk/state.db` + `telemetry.json` + `events.jsonl` (same sources Vizor already reads today) → typed dataclass → surface renders. No surface reads `.synlynk/` files directly — `uxcore` is the only file-format-aware code, so a future storage format change touches one module.

**Write:** keypress/click/API call → surface calls `uxcore.dispatch()` (etc.) with `actor` → `_execute_write()` checks `list_capabilities(actor)` → if permitted, runs existing dispatch/`gh` subprocess plumbing → appends event to `events.jsonl` → returns `WriteResult(ok, message, job_id?)`. If not permitted, returns `WriteResult(ok=False, message="not permitted")` — same shape as a runtime failure, so surfaces don't need a separate permission-denied code path.

## Error Handling

1. **`uxcore` call fails outright** (bad args, file I/O error) → raises typed `UxCoreError`; surfaces catch and display in their own idiom (curses status line / Vizor toast / notifier logs-and-skips). Never a bare traceback reaching a user.
2. **Underlying operation "succeeds" but is actually wrong** — the `exit_code: 0` problem this project has hit repeatedly (Qwen's memory-guard rejections in the recent local-agent A/B test, `synlynk jobs` status unreliability documented in project memory #202). `uxcore` is responsible for parsing the actual result out of subprocess/log output, not trusting exit code alone, and encoding that distinction in `WriteResult`/job status. This is a real behavior change from today's `synlynk jobs`, fixed once inside `uxcore` rather than patched per UI surface.
3. **Stale/conflicting state** (two writers, event log head moved underneath you) → surfaces show a "state changed, refresh" indicator rather than silently overwriting, tying into the pull-before-write guardrail already planned for the event log in the v0.9.0 roadmap item.

## Testing

- `uxcore` functions are unit tested against fixture `.synlynk/` state (existing pattern in `tests/test_local_agent.py`), asserting on returned dataclasses — no live dispatch needed.
- `tui.py` panels are tested by rendering from fixture `uxcore` results into a curses pad buffer — no real terminal or live state required.
- Vizor route tests are rewired to assert against `uxcore` mocks instead of re-deriving expected output inline.
- The Slack notifier is tested by feeding a fixture event stream and asserting on the constructed webhook payload — no real Slack call in tests.

## Phasing

1. **`uxcore` extraction** — refactor `generate_viz_data()` into `uxcore` reads; Vizor's output is regression-tested against current behavior before any TUI code exists.
2. **`uxcore` write path + actor/RBAC/capability-manifest/feature-flag seams** — added to `uxcore`, exercised first via Vizor's existing routes (Vizor already has a UI to click "dispatch" through).
3. **`tui.py`** — built against the now-stable `uxcore`, reusing panels 1:1 with Vizor's information architecture.
4. **Vizor write routes** (dispatch/approve/kill from the browser) — added using the proven write path.
5. **Slack notifier** — built last, once `subscribe()`'s payload shape is settled by real internal use (TUI + Vizor both consuming events).

## Open Questions / Risks

- `generate_viz_data()`'s current implementation has not been read in full during this brainstorm — the refactor in Phase 1 may surface presentation logic that's harder to cleanly separate from data-fetching than assumed here. Should be confirmed early in planning.
- Curses headless/pad-based rendering for panel tests should be prototyped early — if it proves awkward, panel testing strategy may need to change without affecting the rest of the design.
